# 権限の設計

Yorikiの権限（誰が何を見て、使い、変えられるか）と、Runが誰の権限で何を読みどこへ出せるかを定める。対象はSkill・Connector・タスク・入口（Trigger）・出口（配信先）と、管理画面の操作。製品の要件は [design.md](design.md) を正とし、権限については本書を正とする（design.md §3.6・§4.1・§4.9.1・§10.0は本書の要約）。Djangoでの書き方は [backend-conventions.md](backend-conventions.md) §6.3、画面の出し分けは [frontend-conventions.md](frontend-conventions.md) §6 に従う。

- 版：0.1 設計案（2026年10月27日。design.md 0.33）
- タスク・入口・出口はまだ実装していない。その部分は方針で、細部はタスク・配信の段階で実物に即して詰める。

---

## 0 前提

Yorikiは社内向けのAIエージェント基盤。社員は会話でエージェントに業務を頼み、定型の業務はタスクとして自動で動かす。

| もの | 中身 |
|---|---|
| Skill | 業務の手順・判断基準・資料（CSV・PPTX等）・業務結果の形。Draft（編集中）と不変の版を持ち、「公開」で版を作る。エージェントが会話からSkillを直すこともできる（依頼した人の権限の範囲で） |
| Connector | 外部のデータ（社内DB、SharePoint、Google Drive等）を、エージェントに見せる範囲（表・列、サイト・フォルダ）を決めて公開するもの。接続先と資格情報（接続）とは分けて持ち、1つの接続の上に範囲の違うConnectorを複数作れる |
| タスク | 決まった入口（スケジュール・Webhook・チャット等）で起動し、決まったSkill・Connector・Tool・モデル・プロンプトを使い、決まった出口（配信先）へ結果を届ける定型の業務。まだ実装していない |
| 入口（Trigger） | タスクを起動するもの。スケジュール、社内・社外のサービスからのWebhook等 |
| 出口（配信先） | タスクの結果を届ける先。画面の通知、Slack・Teams等のチャット（本人へのDMを含む）、Zapier、Webhook等。メールの送信は持たない（必要ならZapierを通す） |
| 会話 | 社員がエージェントに頼む場。`/`でSkill、`@`でConnectorを指定できる。指定がなければ、エージェントが利用者の使えるものから探して使う |
| Run | 会話の1回の依頼、またはタスクの1回の実行 |

## 1 原則

1. **権限は「所属」と「permission」の2軸で判定する**。所属はどの部門のものを扱えるか、permissionは何ができるかを表す。
2. **Groupは判定に使わない**。Groupはpermissionの集まりで、ユーザーに付けると中のpermissionをまとめて持つ。名前・中身・数は導入先が自由に変えてよい。
3. **部門は人の集まりで、入れ子にしない**。特別な部門も、部門の中の役割も持たない。
4. **複数の部門にまたがるものは作らない**。部門のものは1つの部門に属する。複数の部門で要るものは、部門ごとに作るか、全社・システムのものにする。
5. **Skillは権限を持たない**。Skillは手順と判断基準で、許可を狭めることはできても、広げることはできない。何を読みどこへ出せるかは、Runの実行許可（§6）で決まる。
6. **権限を広げうるものは信頼された強い役割だけが扱い、本人の権限の中で完結するものは本人が扱う**。
7. **信頼しない入力は、権限を変えない**。Webhookのpayload、添付、読み込む文書、Connector・Toolの結果はデータであり、指示として扱わない。何が書かれていても、実行許可は変わらない（§8）。

## 2 範囲

Skill・Connector・タスク・入口・出口は、範囲（個人・部門・全社・システム）を持つ。**範囲は「所有と管理の単位」**で、誰が定義を管理できるかと、どのRunから使えるかの候補を決める。Runが誰の権限で動くかは、範囲ではなく起動のしかたで決まる（§6）。

| 範囲 | 所有 | 管理する層 |
|---|---|---|
| 個人 | 作成者 | 本人 |
| 部門 | 1つの部門 | 業務の管理（Connector・入口・出口は基盤の管理） |
| 全社 | 全社 | 業務の管理（Connector・入口・出口は基盤の管理） |
| システム | システム | 基盤の管理 |

- 一覧の絞り込みは範囲で切り替える（個人は作成者、部門は部門、全社・システムは条件なし）。
- 全社のものは、全社員が自分の見える範囲で使う共通のもの。システムのものは会話には出さず、システムタスクだけが使う。

## 3 3つの層

| 層 | 誰が | 何をする | 判定 |
|---|---|---|---|
| 利用 | 全社員 | 個人・部門・全社のSkill・Connectorを見る・使う、チャットから起動できるタスクを起動する | 範囲と所属だけ |
| 業務の管理 | 部門・全社の業務担当（非技術者が中心） | 部門・全社のSkillの編集・公開、部門・全社のタスクの作成・管理（基盤の管理が用意したConnector・入口・出口から選ぶ） | 範囲と所属と、範囲ごとのpermission |
| 基盤の管理 | 信頼された強い役割（技術者・システム管理者・ユーザー管理者） | 部門・全社・システムのConnector・入口・出口、接続、システムのSkill・タスク、LLM・Runtime Profile・SSO、ユーザー、部門と所属 | permissionだけ（所属は問わない） |

## 4 人と所属

### 4.1 所属と、部門を返す2つの関数

- 所属は「人 × 部門」の割り当て。兼務してよい。異動は日常的にあり、所属の付け外しはユーザー管理者の通常の作業。
- 判定は次の2つの関数にまとめ、すべての判定でこれを使う。

| 関数 | 返すもの | 広げるpermission |
|---|---|---|
| 使える部門（`usable_departments(user)`） | 所属している部門。`can_use_all_departments`か`can_manage_all_departments`を持てばすべての部門 | `user.can_use_all_departments`、`user.can_manage_all_departments` |
| 管理できる部門（`manageable_departments(user)`） | 所属している部門。`can_manage_all_departments`を持てばすべての部門 | `user.can_manage_all_departments`だけ |

- 例：`can_use_all_departments`に部門のSkillの編集を付けても、変えられるのは自分の所属部門のSkillだけ（管理できる部門は広がらない）。
- `can_manage_all_departments`は、すべての部門のデータを使い、すべての部門の業務を管理できる強い権限。
- 部門タスクのチャットからの起動は、実際の所属だけで判定する（`can_use_all_departments`は効かない。監査のための権限で業務を動かさない）。`can_manage_all_departments`は管理できる部門として効く。
- **基盤管理者（`is_superuser`）はアプリの判定に持ち込まない**。Djangoの`has_perm()`は有効なsuperuserにすべてのpermissionを返すので、アプリはいつもpermissionだけで判定し、`is_superuser`を見るコードを書かない。superuserは`can_manage_all_departments`も持つので、2つの関数がそのまますべての部門を返す。
- `is_superuser`を見るのは、アプリの外側の2か所だけ：Django管理画面と、SSOの障害時のパスワードでのログイン（SSOが有効でも基盤管理者だけはパスワードでログインできる非常口）。
- `is_superuser`はフロントエンドに渡さない。画面の出し分けは`allPermissions`と、サーバーが判定した操作の可否（例：ユーザーの管理の`can_change`・`can_issue_invitation`）だけで行う。
- 個人のもの（Skill・Connector・タスク・入口）は「持ち主だけ」で判定し、permissionを見ないので、基盤管理者にも画面とAPIでは見えない（DB・バックアップまで隠すものではない）。

#### 4.1.1 ログイン後に返す本人の情報

ログインした後に最初に取る本人の情報（`app/v1/my/`）は、画面の出し分けの元になるものをすべて返す。フロントエンドは、これと詳細のAPIが返す操作の可否だけで表示を決め、所属やpermissionの規則を作り直さない。

| 項目 | 中身 | 画面での使い道 |
|---|---|---|
| `allPermissions` | 本人が持つすべてのpermission（Group経由と直接を含む。superuserはすべて） | メニュー・ページ・ボタンの出し分け |
| `departments` | 実際に所属している部門 | 本人の所属の表示、部門タスクのチャットからの起動の候補 |
| `usableDepartments` | 使える部門（§4.1の関数の結果） | 一覧の絞り込みの選択肢 |
| `manageableDepartments` | 管理できる部門（§4.1の関数の結果） | 部門のSkill・タスクを作るときの部門の選択肢、作成ボタンの出し分け |

- `is_superuser`は返さない。
- 1件ごとの操作の可否（このSkillを公開できるか等）は、詳細のAPIがサーバーで判定して返す。

### 4.2 人の例（Groupで表す）

| 人 | 付けるもの |
|---|---|
| 一般の社員 | 所属だけ |
| 部門のSkill編集者・公開者 | 所属 ＋ 部門のSkillの編集（・公開） |
| 部門のタスク管理者 | 所属 ＋ 部門のタスクの管理 |
| 全社のSkill公開者 | 全社のSkillの編集・公開 |
| 全社のタスク管理者 | 全社のタスクの管理 |
| 全件利用者（監査等） | `can_use_all_departments` |
| 全件管理者 | `can_manage_all_departments` ＋ 部門・全社のSkill・タスクのpermission |
| Connector管理者（技術者） | 共有のConnectorと接続のpermission |
| システム管理者 | システムのSkill・タスクのpermission |
| 連携の管理者（技術者） | 部門・全社・システムの入口と出口、Slack・Teams等への接続のpermission（Connector管理者が兼ねることが多い） |
| ユーザー管理者 | ユーザー、部門と所属のpermission |
| 基盤管理者 | `is_superuser`（すべてのpermissionを持つ人。非常口のログインとDjango管理画面） |

Connector管理者・連携の管理者・システム管理者・ユーザー管理者は、信頼された強い役割として割り切る。部門のタスク管理者は、部門のデータ（会話でも読めるもの）を、その部門に許された出口へ出せる役割として扱う。例えばユーザー管理者は、アカウントを作り所属を決められるので、本質的にどの部門の人にもなれる（SSOが有効なら招待・再設定のリンクは使えず、この経路はパスワードのアカウントでだけ起きる）。

## 5 問い1：誰が定義を管理できるか

### 5.1 Skill

| 範囲 | 役割 | 見る・使う | Draftを変更する | 公開・切戻し・停止・削除 |
|---|---|---|---|---|
| 個人 | 個人の作業のやり方、試作 | 本人 | 本人 | 本人 |
| 部門 | 部門の正式な業務手順 | 使える部門 | 管理できる部門 ＋ `skill.can_edit_department_skills` | 管理できる部門 ＋ `skill.can_publish_department_skills` |
| 全社 | 全社員が使う共通の手順 | 全員 | `skill.can_edit_company_skills` | `skill.can_publish_company_skills` |
| システム | システムタスクの手順 | システム管理者 | `skill.can_edit_system_skills` | `skill.can_publish_system_skills` |

- 公開のpermissionはDraftの変更を含む。評価ケースの作成・変更は編集の権限、「公開の前に必須」の印の付け外しは公開の権限。
- 範囲は通常の操作では変えない（必要なら新しく作る）。組織の再編での付け替えは §9。
- エージェントが会話からSkillを直すときも、依頼した人の権限で同じ判定をする。

### 5.2 Connector

| 範囲 | 役割 | 資格情報 | 見る・使う | 作成・編集・削除 |
|---|---|---|---|---|
| 個人 | 自分のファイル（OneDrive・Google Drive等）を読ませる | 本人のOAuthのtoken | 本人 | 本人 |
| 部門 | 部門の業務データ | 共有の資格情報 | 使える部門 | Connector管理者（`connector.add/change/delete_connector`） |
| 全社 | 全社員に見せてよい共通のデータ | 共有の資格情報 | 全員 | Connector管理者 |
| システム | システムタスクだけが使うデータ | 共有の資格情報 | システム管理者・Connector管理者（定義だけ） | Connector管理者 |

- 接続（接続先と資格情報）は、permission（`connector.view/add/change/delete_<接続のModel>`）だけで判定する。
- 個人Connectorは、本人のtokenで読めるもの（本人に共有された他部門のファイルを含む）を読める。本人の権限を超えないので本人が作れる。外へ出す経路は §7で絞る。
- Connectorの範囲（どの表・列、どのサイト・フォルダ）はサーバー側で操作のたびに強制する。

### 5.3 タスク

| 範囲 | 役割 | 定義を見る・作る・変える | チャットから起動する（印があるとき） |
|---|---|---|---|
| 個人 | 自分の作業の自動化 | 本人 | 本人 |
| 部門 | 部門の正式なワークフロー | 管理できる部門 ＋ `task.can_manage_department_tasks` | その部門に実際に所属する人、管理できる部門の人 |
| 全社 | 全社員に提供する共通の業務（弱い権限で済むもの） | `task.can_manage_company_tasks` | 全員 |
| システム | 強い資格情報が要る業務（複数の部門のデータの突き合わせ等） | `task.can_manage_system_tasks` | 不可 |

- 部門・全社・システムのタスクの定義（指示、使うもの、入口と出口）は、管理できる人だけに見せる。一覧も同じ規則で絞り、起動できる人には起動の候補として名前と説明だけを見せる。
- 管理できる人なら誰でも直せる（1人の担当者に依存しない）。
- 横断の業務（全社Connector以外のデータが要る全社の業務）はシステムタスクにする。業務担当が要件と評価ケースを出し、システム管理者がConnector・入口・出口を決めて作る。

### 5.4 タスクが固定するもの

タスクの定義は、使うSkillの版、Connector、Tool、モデル設定、入口、出口、入力の形と制限を固定して持つ。**タスクの定義にも版を持たせ**、Runは受付時のタスクの版に固定する（§6）。

- **Skillは版を固定する**（ライブラリの依存と同じ）。Skillが新しい版を公開しても、タスクは自動では切り替わらない。版を上げるのはタスクの変更で、タスクを管理できる人が差分を見て行う（画面で「新しい版があります」と知らせる）。
- タスクに登録できるもの：

| タスクの範囲 | Skill | Connector | 入口・出口 |
|---|---|---|---|
| 個人 | 本人が使えるSkill | 本人が使えるConnector（個人Connectorを含む） | 本人のスケジュール、画面の通知、本人へのDM |
| 部門 | その部門の部門Skill、全社Skill | その部門の部門Connector、全社Connector | その部門に許された入口・出口 |
| 全社 | 全社Skill | 全社Connector | 全社に許された入口・出口 |
| システム | システムSkill | システムConnector、部門Connector（どの部門も）、全社Connector | システムに許された入口・出口 |

- 部門・全社・システムのタスクには、個人のSkill・Connector・入口・出口を登録できない。
- **タスクのRunでは、Connectorを指示で選ばせない**。エージェントが使えるConnectorはタスクに固定したものだけで、会話のように利用者の使えるものから探して使うことはしない。プロンプト・Skill・入力に何が書かれていても増えない。
- 入力の制限：入力の項目ごとに、型と取りうる値（選べる対象）を決められる。Connectorの操作には取得件数の上限があり、タスクごとにさらに絞れる。Toolの引数も、タスクごとに絞れる。
- Tool：Skillの「使ってよいTool」とタスクのToolの一覧の、両方に入っているものだけを使う。どちらにも書いていなければ、Toolなし（文章の応答だけ）。汎用のコード実行・ファイルの書出しも、この一覧で絞る。コードを実行する環境（Sandbox）は、Connectorの資格情報と外のネットワークに直接届かない。

### 5.5 入口と出口

入口（Trigger）と出口（配信先）は、Connectorと同じく、部門・全社・システムのものは強い権限者（連携の管理者）が作る。Slack・Teams・Zapier等の外のサービスとつながり、データの出入り口になるため。

| 範囲 | 例 | 作る・変える人 |
|---|---|---|
| 個人 | 本人のスケジュール（入口）、画面の通知・本人へのDM（出口） | 本人 |
| 部門・全社・システム | スケジュール、Webhook（入口）、画面の通知、Slack・Teamsのチャンネル、Zapier、Webhook（出口） | 連携の管理者（Django標準のpermission。所属は問わない） |

- 部門・全社・システムの入口・出口は、作るときに使ってよい範囲（どの部門・全社・システム）を決める。一度許したら、その範囲のタスクは自由に付けてよい（タスクごとの承認はしない）。
- **Webhookの入口とタスクは1対1** にする。1つの鍵で起動できるのは1つのタスクだけで、入口の画面にはそのタスクを表示する（鍵を持つ送り元が、後から付けたタスクまで起動できないように）。入口のタスクを付け替えるときは鍵を作り直す。スケジュールの入口は、タスクごとに持つ。
- 出口を作る人は、実際の受信者（チャンネルの参加者、連携先の先）が許す範囲に合うかを確かめる。受信者の変更も、権限の変更と同じ重さで扱う。
- 入口を作る人は、Webhookの鍵を誰（どのサービス）に渡すかを確かめる。鍵を持つ送り元は「そのタスクが読めるものを、そのタスクの出口へ出させる」力を持つ。入口ごとに、送り元の認証（APIキー・署名）、重複の判定、受け取る項目の型と取りうる値を決める。
- メールの送信は持たない（宛先を毎回変えられる送信は持ち出し口になりやすく、気軽に使われるため）。必要ならZapierを出口にして、Zapier側で送る。
- **個人の出口は、画面の通知と本人へのDMだけ**にする。DMの宛先は本人に固定し、YorikiのアカウントとSlack・Teamsのユーザーの対応はメールアドレスの一致等で確かめたものを使う。Slack・Teamsへの接続（アプリ・bot）は連携の管理者が用意し、個人は接続を作らない。本人が作るWebhook等を出口に許すと、本人が読めるもの（本人に共有された他部門のファイルを含む）を自動で外へ流せるため、許さない。

## 6 問い2：このRunは誰の権限で動くか（実行許可）

Runを受け付けるときに、**実行許可**を組み立ててRunに固定する。実行許可は、誰の権限か、使えるSkill・Connector・Tool、出口、入力の条件を持つ。操作のたびに実行許可と照合する。

| 起動のしかた | 対象のタスク | 誰の権限 | 実行許可の中身 |
|---|---|---|---|
| 会話 | （タスクではない） | 依頼した人 | 依頼した人が使えるSkill・Connector、利用者に許されたTool。出口は依頼した人への応答 |
| チャットからのタスクの起動 | 個人・部門・全社 | 起動した人 | タスクに固定したもの。起動した人がそのすべてを使えなければ起動前に断る。操作のたびに「タスクの版の一覧 ∩ 起動した人の今の権限」で判定する（権限を失えばその操作は断る。権限が増えても、タスクの版の一覧の外は使えない） |
| 入口（スケジュール・Webhook） | 個人（スケジュールだけ）・部門・全社・システム | タスクの範囲（個人タスクは本人） | タスクに固定したもの |
| 管理画面からの手動実行 | 部門・全社・システム | タスクの範囲 | タスクに固定したもの。実行できるのはタスクを管理できる人 |

- 「人が自由に指示を出せる起動（会話・チャット）は、その人の権限を超えない。人が指示を出せない起動（入口・手動実行）は、タスクに固定したものの範囲で動く」と整理する。
- 個人タスクはどの起動でも本人の権限で動く。入口からの起動で個人Connectorの本人のtoken（refresh token）を使うのは、本人がそのタスクの無人実行を明示的に有効にしたときだけ。tokenの失効、本人の無効化で止まり、再認可の手段を用意する。
- **タスクのRunは、会話の文脈を引き継がない**。チャットから起動しても、文脈はタスクの定義と入力だけで組み立てる（会話に残った、もう使えない部門の情報をタスクの出口へ流させないため）。
- **人のいない起動は、指示を受け取らない**。対話の連携（Teams・Slack等のスレッド）があっても、チャネルの参加者ができるのは、エージェントが尋ねた質問への回答と停止だけで、追加指示は受け付けない。回答は質問への答えとしてだけ取り込み、実行許可は変わらない。
- 人が起動したRunでも、スレッドから追加指示を出せるのは、そのRunを起動した本人（Yorikiのアカウントに紐付いた人）だけ。ほかの参加者は回答と停止だけ（起動した人の権限で、ほかの人の指示を実行しないため）。
- 入口と手動実行で受け取るのは、タスクの定義で型を決めた入力（項目・値・ファイル）だけで、自由な依頼文は受けない。指示はタスクの定義（プロンプト・Skill）にだけある。
- 会話のTool：「利用者に許されたTool」∩「そのRunに許されたTool」∩「Skillの指定」だけを使う。将来、会話に外へ出すTool（メールの送信等）を足すときは、利用者本人の送信の権限で動かし、宛先をRunの中で確定する。Skillが送信の権限を与えることはない。
- **再実行とリトライ**：
  - 再実行（利用者・管理者が「もう一度」を選ぶ）は、今のタスクの定義で新しいRunを作り、入力だけを引き継ぐ。実行許可は今の権限で組み立て直す。
  - リトライ（障害からの自動の再試行）は、同じRunの続きとして元の実行許可で行う。実行許可の中のものが停止・削除・範囲の変更で外れていたら、リトライせずに失敗にする。
  - キューで待っているRunは、受付時のタスクの版のまま動く（会話の「Runの中では固定」と同じ）。タスクの定義を直しても、待っているRunは失敗させない。止めたいときはタスクを停止し、停止は待っているRunにも効く。
  - 出口への配信は、Run・出口・送る項目ごとの安定したIDで重複を防ぎ、連携先に重複を防ぐ仕組みがあれば使う。送ったかどうか分からない障害では、自動で送り直さず、確認待ちにする。
- **確かめ直すとき**：受付時、キューから実行を始めるとき、出口への配信・外への送信の直前に、タスクが停止されていないか、実行許可の中のもの（Skill・Connector、出口）が今も有効で範囲の中にあるか、起動した人・本人が今も有効で権限を持つかを確かめ、外れていれば実行・配信しない。実行中に権限が変わったら、次のConnectorの操作から効く。長く動くRunは、管理者が取り消せる。
- Runには、実行許可、起動のきっかけ（起動した人・入口と送り元）、最後にタスクを保存した人、固定した版と入力を記録する。

### 6.1 Runと会話（固定はRunの中だけ）

- 会話の1つのRunは、利用者の1つの依頼に対して、エージェントがLLMとToolの呼出しを繰り返し、結果を返すまでのひとまとまり。実行中の追加指示、確認待ちからの再開、障害からの試行（Attempt）も同じRunの中。
- 実行許可と版（Skill・モデル設定・タスク）の固定は、**Runの中だけ**。会話をまたいでは固定しない。同じ会話でも、次の依頼のたびに、その時点の権限と最新の公開版で実行許可を組み立て直す（会話は何日も続き、その間の異動・権限の変更・Skillの改善を反映するため）。
- 会話は文脈を引き継ぐので、Runの境目で次のことが起きる。
  - 前のRunで読んだSkillの古い版が文脈に残る。次のRunで新しい版を読み込むときは、前に読んだ版に代わるものであることをモデルに明示する。
  - 権限を失った後も、前のRunで読んだデータ（Connectorの結果等）は文脈に残り、次のRunのエージェントも見える。利用者がすでに見た内容なので、**許容する**（文脈から外すことはしない）。ただし次のRunでは、使えなくなったConnectorをもう呼べない。

## 7 問い3：このRunは何を読み、どこへ出せるか

- 読めるもの：実行許可のSkill・Connectorだけ。Connectorの範囲は操作のたびに強制する。
- 出せる先：

| 出す経路 | 規則 |
|---|---|
| 会話の応答 | 依頼した人・起動した人に返す（その人が使えるものだけで作った結果なので、その人に見せてよい） |
| タスクの出口 | 実行許可の出口だけ（§5.4でタスクの範囲に許されたものに限っている） |
| 書込み（書込みのConnector等） | 今は持たない。入れるときは強く制限し、**書込みも出口として扱う**。書込み先はタスクに許されたもの（タスクの範囲に含まれるもの）だけで、対象を限定して明示的に許可する。部門のデータを全社の書込み先へ保存して、出口を通さずに広げることはできない |

- 部門タスクが部門のデータを全社向けの出口へ流すことはできない（出口の範囲で塞ぐ）。全社へ出す必要がある業務は、システムタスクとして作る。
- 個人タスクの出口は、画面の通知と本人へのDMに限る。

### 7.1 Runの結果とログを見られる人

ログ（Toolの呼出しと結果、内部の記録、エラー、入力）を見られるのは、そのものを管理できる人だけ。結果（最後の応答、業務結果、成果物）とログは分けて持つ。

Runには、実行したときのタスクの範囲と部門を記録し、結果・ログ・成果物を見られるかは、タスクの今の範囲ではなくこの記録で判定する（タスクを別の部門・全社へ移しても、移す前のRunは、移す前の範囲を管理できる人だけが見られる）。

Runの中身が外へ出る経路をすべて列挙し、どれにも「結果」か「ログ」の判定を当てる：一覧・詳細のAPI、検索、SSE（実行中の進み具合）、RunEvent、エラーの本文、添付・成果物のダウンロードと期限付きURL、出口への配信の履歴。期限付きURLは、結果を見られる人にだけ発行し、対象と期限を限る。

| Run | 結果 | ログ |
|---|---|---|
| 会話 | 依頼した人 | 依頼した人（本人の会話なので本人が管理する） |
| 個人タスク | 本人 | 本人 |
| 部門・全社タスク（チャットから起動） | 起動した人とタスクを管理できる人 | タスクを管理できる人 |
| 部門・全社タスク（入口・手動実行） | タスクを管理できる人（出口へ届けたものは出口の受信者） | タスクを管理できる人 |
| システムタスク | システムタスクを管理できる人（出口へ届けたものは出口の受信者） | システムタスクを管理できる人だけ |

### 7.2 実装の形

権限の判定は、規則がずれないように集め、効率よく絞る。

- **所属の判定**は、`user`の2つの関数（使える部門・管理できる部門）だけで行う。ほかの場所では所属を直接引かない。リクエストの中で1回だけ計算して`request.user`に持たせる（permissionはDjangoがユーザーごとにキャッシュしている）。キャッシュは読むだけに使い、権限・所属を変える処理の後では使わない。Workerはユーザーの情報を使い回さず、確かめ直すたびにDBから読む。停止と外への送信がぶつかる場面は、行ロックと冪等のIDで扱う。
- **ものごとの判定**は、各アプリのQuerySetとModelに置き、Viewには書かない。
  - 一覧の絞り込み：`<Model>.objects.visible_to(user)`・`manageable_by(user)`。
  - 1件の判定：`obj.can(user, 操作)`。操作は「見る・使う・管理・起動・結果を見る・ログを見る・候補に出す」を区別する（`access_of(user)` 1つでは操作の違いを表せない）。
  - 範囲ごとに「誰が見る・使う・変えるか」を1つの規則表に書き、QuerySetとModelの両方がそれを読む。
  - Viewは`get_queryset`でQuerySetの絞り込みを使い、操作ではModelの判定を呼ぶだけ。一覧では隠れるのにIDを指定すると読める、という食い違いを構造で防ぐ。
  - Serializerの関連の項目（Connector・Skill・入口・出口のID）の選択肢も同じ判定で絞り、保存の直前にも確かめる（画面に出ないIDを登録させない）。
  - Worker（Django Q2）や管理コマンドでも、`request`に頼らず同じ判定を呼ぶ。Q2にはIDだけを渡し、WorkerがDBからRunと実行許可を読み直して判定する。
  - 一覧（QuerySet）と1件の判定が同じ結果になることを、操作ごとにテストで保証する。
- **一覧の効率**：部門のID・範囲・持ち主・有効の条件でSQLで絞り、1件ずつ判定しない。これらの列に索引を置く。
- **実行許可の保存**：Runには、誰の権限か・起動の種類・タスクの版・固定した版（Skill・モデル設定・Connector）だけを保存し、操作のたびに対象だけを判定する。使えるもの全件の一覧は持たない。例外として、会話のRunがエージェントに見せるSkillの一覧（名前とID）は、Runの中で変わらないように開始時に固定する。
- **参照先の版**：タスクの版が同じでも、参照先（Connectorの対象の列、出口のチャンネル）の変更はすぐ効く（管理者の責任）。Runには使ったConnectorの版を記録し、出口にも変更の履歴を持たせて監査で追えるようにする。止める仕組みは作らない。
- **候補のAPIと設定のAPIを分ける**：タスク・Skillの編集画面で選ぶ候補（Connector・入口・出口）は、ID・名前・用途・範囲だけを返す専用のAPIにし、資格情報や接続の設定を返すAPIとは分ける。
- **テスト**：superuserでは判定のテストをしない（存在しないpermissionの名前でも通り、書き間違いを隠すため）。必要なpermissionだけを付けたユーザーで試す。一覧で件数が増えてもクエリの数が増えないことも確かめる。すべての役割の組み合わせではなく、境界ごとに重点を置く（範囲ごとの見る・使う・変える、一覧・詳細・Runの履歴で判定が同じか、許された読取りから許されない出口への流れ、定義の変更後のリトライ、待っているRunとタスクの停止）。

### 7.3 画面

画面は層で分ける。業務画面は「自分の所属から見える」場所、管理画面は「所属を問わず、すべてを扱う」場所。

| 層 | 画面 |
|---|---|
| 利用・業務の管理 | 業務画面（ルート直下）。同じ画面の中で、できることに応じて編集・公開のボタンが出る |
| 基盤の管理 | 管理画面（`/manage`）。一覧は所属で絞らず、permissionだけで決まる |

- `/manage`の入口は、管理画面のメニューに出せる項目があるときだけ出る（基盤の管理のpermissionを持つ人だけ）。部門のSkillの公開者・部門のタスク管理者は管理画面に入らない。
- 会話の`/`・`@`の候補は、業務画面の「使える」一覧と同じQuerySetから作る。

| もの | 業務画面 | 管理画面 |
|---|---|---|
| Skill | `/skills`：個人・部門・全社 | システムSkill（`/manage/system_skills`。Skillの編集の部品を使い回す） |
| Connector | `/connectors`（使えるConnectorを見る、個人Connector。Connectorの会話での利用の段階で作る） | `/manage/connectors`：部門・全社・システム（全件） |
| 接続先 | — | `/manage/database_connections` |
| タスク | `/tasks`：個人・部門・全社 | システムタスク（`/manage/system_tasks`） |
| 入口・出口 | 個人の出口（画面の通知・本人へのDM）はタスクの編集の中で選ぶ | 部門・全社・システムの入口・出口 |
| Runの結果・ログ | 会話の画面（本人）、タスクの詳細（管理できる人） | システムタスクの詳細 |
| ユーザー・部門・SSO・LLM・Runtime Profile | — | `/manage` |

#### 7.3.1 業務画面の一覧（Skill・タスク共通の形）

範囲で絞った一覧から、選んで詳細（編集）に入る。

```
[個人] [部門 ▼経理部] [全社]        □ 編集できるものだけ      [＋ 作成]
──────────────────────────────────────────
請求書の照合   部門・経理部   公開中 版5   編集・公開できます
名寄せ         個人           公開中 版2   編集・公開できます
議事録の要約   全社           公開中 版8   使えます
```

- 範囲のタブ：個人・部門・全社。システムは出さない。
- 部門の選択肢は、Skillは`usableDepartments`、タスクは`manageableDepartments`。
- 行ごとの「できること」は、サーバーが判定した可否を出す。
- 作成ボタンは作れる範囲があるときだけ出す（個人はいつでも、部門は`manageableDepartments`と部門の編集・管理のpermission、全社は全社のpermission）。作成の画面で選べる範囲と部門も同じ規則で絞る。

| | Skill（`/skills`） | タスク（`/tasks`） |
|---|---|---|
| 一覧に出るもの | 使えるもの全部 | 管理できるものだけ（定義は管理できる人だけに見せる） |
| 「編集できるものだけ」 | 要る | 要らない |

- チャットから起動できるタスクは、`/tasks`には出さず、会話の入力欄の候補として出す。

## 8 信頼しない入力とプロンプトインジェクション

信頼しない入力：Webhookのpayload、添付・読み込む文書（PDF・Office・CSV等）、Connector・Toolの結果、Webから取得したもの。

- **守りは制約で行う**：信頼しない入力に何が書かれていても、実行許可（Skill・Connector・Tool・出口）は変わらない。Skillの公開・変更、出口の変更、権限の変更をするToolは、タスクのRunには渡さない。出口の宛先は出口の定義で決まり、入力からは変えられない。
- 指示ではない入力でも、許された操作の中で誘導はできる（Webhookの値を検索の条件にして大量に取得する等）。これは入力の型と取りうる値、取得件数の上限、Toolの引数の制限で絞る（§5.4）。
- **補助**：信頼しない入力は、モデルに渡すときに区切って「データ」であることを明示する。
- **後で足せる補助**：入力に指示が含まれるかを判定する仕組み（ガード用のモデル等）。誤検知と見逃しがあり、判定するモデル自体もだまされうるので、止めるためではなく記録と通知のために使う（出口・書込みのあるタスクで、信頼しない入力だけを判定し、疑わしいものを管理者へ知らせる）。入れなくても設計は変わらない。
- 会話で社員が添付した文書も同じ扱い。添付の中の「Skillを書き換えよ」等を、利用者の依頼として扱わない。

## 9 部門の再編と削除

- 部門は削除せず、無効にする。無効にした部門のもの（Skill・Connector・タスク・入口・出口）は新しく使えず、タスクは起動しない。所属・Runの履歴は残す。
- 部門のSkill・Connector・タスク・入口・出口を別の部門・全社へ移す操作は、組織の再編のための別の操作とする（基盤の管理）。移す前に、影響（使えるようになる人、そのものを使うタスク、出口の受信者）を表示して確認させる。過去のRunの結果・ログは移した先へは見せない（§7.1。実行したときの範囲と部門で判定する）。移す間は、それを使うタスクを止め、移った先で有効にし直す。

## 10 基盤の管理

- 管理APIはすべてpermissionで判定する。対象：部門・全社・システムのConnector・入口・出口、接続、システムのSkill・タスク、LLMの接続・モデル設定、Runtime Profile、SSOの設定、ユーザー（招待のリンクの発行を含む）、Groupの一覧（割り当ての選択肢）、部門と所属。Django標準のpermission（view・add・change・delete。changeを持てばviewもできる）か、範囲ごとのpermissionを使う。
- permissionの指定を書き忘れた操作を閉じる既定（`DEFAULT_PERMISSION_CLASSES`）は、誰も通さないものにする（superuserも通さない。書き忘れはテストですぐ分かる）。`PlatformAdmin`はなくす。
- 委任したときの防止策（強い役割の中での事故を減らすためのもの）：
  - ユーザーの更新APIで書ける項目は、表示名・有効・Group・所属だけ。permissionの直接付与、`is_superuser`、SSOの識別子はAPIに出さない。
  - 自分の所属・Groupは変えられない。
  - 自分の持たないpermissionを含むGroupは、誰にも付け外しできない。
  - 自分の持たないpermissionを持つアカウント（基盤管理者を含む）は、変更も招待・再設定のリンクの発行もできない。発行は記録する。画面には、操作する人から見た可否（`can_change`・`can_issue_invitation`）をサーバーが返す。
  - Groupの中身の編集はDjango管理画面（基盤管理者だけ）。

## 12 0.33で変えたこと（以前の設計・実装から）

- Skill：部門の中の役割（利用・編集・公開）をやめ、部門の範囲を所属とpermissionで判定する。部門は1つ（今のまま）。システムの範囲を足す。
- Connector：使える部門（多対多、空なら全社向け）をやめ、範囲（個人・部門・全社・システム）と1つの部門にする。作成・編集は所属を問わずpermissionだけにする。
- 部門の「すべての部門の範囲を含む」印をやめ、`can_use_all_departments`・`can_manage_all_departments`と、使える部門・管理できる部門の2つの関数にする。
- 初期のGroupを`migrate`のたびに作り直す仕組みをやめ、最初に一度だけ作る。
- 基盤管理者だけにしていた管理APIを、すべてpermissionにする。`PlatformAdmin`をなくし、既定は誰も通さないものにする。
- フロントエンドに渡している`is_platform_admin`をなくす。
