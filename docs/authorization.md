# 権限の設計

Yorikiの権限（誰が何を見て、使い、変えられるか）と、Runが誰の権限で何を読みどこへ出せるかを定める。対象はSkill・Connector・タスク・入口（Trigger）・出口（配信先）と、管理画面の操作。製品の要件は [design.md](design.md) を正とし、権限については本書を正とする（design.md §3.6・§4.1・§4.9.1・§10.0は本書の要約）。Djangoでの書き方は [backend-conventions.md](backend-conventions.md) §6.3、画面の出し分けは [frontend-conventions.md](frontend-conventions.md) §6 に従う。

- 版：0.1 設計案（2026年10月27日。design.md 0.33）
- タスク（定義と版、手動実行）・Webhookの入口・出口（Webhook・Zapier・画面の通知）と配信、出口へ渡す成果物の期限付きURLは実装した。タスクの画面（業務画面の `/tasks` と管理画面の `/manage/system_tasks`。一覧・作成・編集・手動実行・版の履歴）、入口の画面（タスクの画面の「入口」のタブと `/tasks/{task}/triggers/{trigger}`。サンプルのpayloadで取り出しを試す）、発行済みの入口の一覧（`/manage/trigger_bindings`。見るだけ）、出口の管理画面（`/manage/destinations`）、タスクのRunの画面（`/tasks/{task}/runs/{run}`。起動のしかたと起動元、入力、作業の記録と応答、成果物、配信の状態と通知の再試行）、タスクをまたいだ実行の履歴（`/runs`）、チャットからのタスクの起動（「チャットから起動できる」の印、会話の入力欄の `/` の候補、起動した会話のカード、起動した人が見られる結果）も実装した。スケジュールの入口、本人へのDM・Slack・Teamsの出口、タスクのRunの再実行（入力を引き継いだ新しいRun）はまだ実装していない。その部分は方針で、細部は各段階で実物に即して詰める。

## 0 前提

Yorikiは社内向けのAIエージェント基盤。社員は会話でエージェントに業務を頼み、定型の業務はタスクとして自動で動かす。

| もの | 中身 |
|---|---|
| Skill | 業務の手順・判断基準・資料（CSV・PPTX等）・業務結果の形。Draft（編集中）と不変の版を持ち、「公開」で版を作る。エージェントが会話からSkillを直すこともできる（依頼した人の権限の範囲で） |
| Connector | 外部のデータ（社内DB、SharePoint、Google Drive等）を、エージェントに見せる範囲（表・列、サイト・フォルダ）を決めて公開するもの。接続先と資格情報（接続）とは分けて持ち、1つの接続の上に範囲の違うConnectorを複数作れる |
| タスク | 決まった入口（スケジュール・Webhook・チャット等）で起動し、定義で使うよう指示したSkill・Connector・モデル・プロンプトで作業し、決まった出口（配信先）へ結果を届ける定型の業務（スケジュールからの起動はまだない） |
| 入口（Trigger） | タスクを起動するもの。スケジュール、社内・社外のサービスからのWebhook等 |
| 出口（配信先） | タスクの結果を届ける先。画面の通知、Slack・Teams等のチャット（本人へのDMを含む）、Zapier、Webhook等。出口としてのメールの送信は持たない（必要ならZapierを通す。招待のリンク等、システムから本人へのメールは出口ではない） |
| 会話 | 社員がエージェントに頼む場。`/`でSkill、`@`でConnectorを使うよう指示できる。指示がなくても、エージェントは利用者がアクセスできるものから探して使う |
| Run | 会話の1回の依頼、またはタスクの1回の実行 |

## 1 原則

1. **権限は「所属」と「permission」の2軸で判定する**。所属はどの部門のものを扱えるか、permissionは何ができるかを表す。
2. **Groupは判定に使わない**。Groupはpermissionの集まりで、ユーザーに付けると中のpermissionをまとめて持つ。名前・中身・数は導入先が自由に変えてよい。
3. **部門は人の集まりで、入れ子にしない**。特別な部門も、部門の中の役割も持たない。
4. **複数の部門にまたがるものは作らない**。部門のものは1つの部門に属する。複数の部門で要るものは、部門ごとに作るか、全社・システムのものにする。
5. **Skillは権限を持たない**。Skillは手順と判断基準で、許可を広げることも狭めることもできない。何を読みどこへ出せるかは、Runの実行許可（§6）で決まる。
6. **権限を広げうるものは信頼された強い役割だけが扱い、本人の権限の中で完結するものは本人が扱う**。
7. **信頼しない入力は、権限を変えない**。Webhookのpayload、添付、読み込む文書、Connector・Toolの結果はデータであり、指示として扱わない。何が書かれていても、実行許可は変わらない（§8）。
8. **利用できることと、使うよう指示することは別の概念**。Runがアクセスできるものは、Skill・Connectorの範囲と本書の権限モデルだけで決まる。会話の `/`・`@`、タスクの定義で選んだSkill・Connector、Skillが宣言したConnector・Toolは、使用の指示で、アクセス範囲を広げも狭めもしない。範囲を定義してあるので、Runやタスクごとに使えるものを列挙しない。Skillについて権限が決めるのは、セッションの権限（会話は開始したユーザー、タスクはタスクの範囲）でそのSkillを選べるかどうかだけで、選んだ後のSkillは手順の指示にすぎない。

## 2 範囲

Skill・Connector・タスク・入口・出口は、範囲（個人・部門・全社・システム）を持つ。**範囲は「所有と管理の単位」**で、誰が定義を管理できるかと、どのRunから使えるかを決める。Runの権限の基準（会話は依頼した人、タスクはタスクの範囲）は §6 で決まる。

| 範囲 | 所有 | 管理する層 |
|---|---|---|
| 個人 | 作成者 | 本人 |
| 部門 | 1つの部門 | 業務の管理（Connector・出口は基盤の管理） |
| 全社 | 全社 | 業務の管理（Connector・出口は基盤の管理） |
| システム | システム | 基盤の管理 |

- 一覧の絞り込みは範囲で切り替える（個人は作成者、部門は部門、全社・システムは条件なし）。
- 全社のものは、全社員が自分の見える範囲で使う共通のもの。システムのものは会話には出さず、システムタスクだけが使う。システムタスクは、システム・全部門・全社のものを使える（§5.4）。

## 3 3つの層

| 層 | 誰が | 何をする | 判定 |
|---|---|---|---|
| 利用 | 全社員 | 個人・部門・全社のSkill・Connectorを見る・使う、チャットから起動できるタスクを起動する | 範囲と所属だけ |
| 業務の管理 | 部門・全社の業務担当（非技術者が中心） | 部門・全社のSkillの編集・公開、部門・全社のタスクの作成・管理（入口の作成を含む。基盤の管理が用意したConnector・出口から選ぶ） | 範囲と所属と、範囲ごとのpermission |
| 基盤の管理 | 信頼された強い役割（技術者・システム管理者・ユーザー管理者） | 部門・全社・システムのConnector・出口、接続、入口の一覧を見ること、システムのSkill・タスク、LLM・Runtime Profile・SSO、ユーザー、部門と所属 | permissionだけ（所属は問わない） |

## 4 人と所属

### 4.1 所属と、部門を返す2つの関数

- 所属は「人 × 部門」の割り当て。兼務してよい。異動は日常的にあり、所属の付け外しはユーザー管理者の通常の作業。
- 判定は次の2つの関数にまとめ、すべての判定でこれを使う。どの関数も、有効な部門（無効にしていない部門。§9）だけを返す。

| 関数 | 返すもの | 広げるpermission |
|---|---|---|
| 使える部門（`usable_departments(user)`） | 所属している部門。`can_use_all_departments`か`can_manage_all_departments`を持てばすべての部門 | `user.can_use_all_departments`、`user.can_manage_all_departments` |
| 管理できる部門（`manageable_departments(user)`） | 所属している部門。`can_manage_all_departments`を持てばすべての部門 | `user.can_manage_all_departments`だけ |

- 例：`can_use_all_departments`に部門のSkillの編集を付けても、変えられるのは自分の所属部門のSkillだけ（管理できる部門は広がらない）。
- `can_manage_all_departments`は、すべての部門のデータを使い、すべての部門の業務を管理できる強い権限。
- 部門タスクのチャットからの起動は、実際の所属（3つめの関数 `joined_departments(user)`。permissionで広がらない）か管理できる部門で判定する（`can_use_all_departments`は効かない。監査のための権限で業務を動かさない）。
- **基盤管理者（`is_superuser`）はアプリの判定に持ち込まない**。Djangoの`has_perm()`は有効なsuperuserにすべてのpermissionを返すので、アプリはいつもpermissionだけで判定し、`is_superuser`を見るコードを書かない。superuserは`can_manage_all_departments`も持つので、2つの関数がそのまますべての部門を返す。
- `is_superuser`を見るのは、次の3か所だけ：Django管理画面、SSOの障害時のパスワードでのログイン（SSOが有効でも基盤管理者だけはパスワードでログインできる非常口）、基盤管理者のアカウントの保護（基盤管理者のアカウントの変更と招待・再設定のリンクの発行・受け入れは、基盤管理者だけ。委任された管理者がすべてのpermissionを持っていても、非常口のアカウントを奪えないように）。
- `is_superuser`はフロントエンドに渡さない。画面の出し分けは`allPermissions`と、サーバーが判定した操作の可否（例：ユーザーの管理の`can_change`・`can_issue_invitation`）だけで行う。
- 個人のもの（Skill・Connector・タスク・入口）は「持ち主だけ」で判定し、permissionを見ないので、基盤管理者にも画面とAPIでは見えない（DB・バックアップまで隠すものではない）。

#### 4.1.1 ログイン後に返す本人の情報

ログインした後に最初に取る本人の情報（`app/v1/my/`）は、画面の出し分けの元になるものをすべて返す。フロントエンドは、これと詳細のAPIが返す操作の可否だけで表示を決め、所属やpermissionの規則を作り直さない。

| 項目 | 中身 | 画面での使い道 |
|---|---|---|
| `allPermissions` | 本人が持つすべてのpermission（Group経由と直接を含む。superuserはすべて） | メニュー・ページ・ボタンの出し分け |
| `departments` | 実際に所属している部門 | 本人の所属の表示、部門タスクのチャットからの起動の候補、会話・個人タスク・個人のSkillの評価で予算を計上する部門の候補（design.md §9.1） |
| `usableDepartments` | 使える部門（§4.1の関数の結果） | 一覧の絞り込みの選択肢 |
| `manageableDepartments` | 管理できる部門（§4.1の関数の結果） | 部門のSkill・タスクを作るときの部門の選択肢、作成ボタンの出し分け |

- `is_superuser`は返さない。
- 1件ごとの操作の可否（このSkillを公開できるか等）は、詳細のAPIがサーバーで判定して返す。

### 4.2 人の例（Groupで表す）

| 人 | 付けるもの |
|---|---|
| 一般の社員 | 所属だけ |
| 部門のSkill編集者・公開者 | 所属 ＋ 部門のSkillの編集（・公開） |
| 部門のタスク管理者 | 所属 ＋ 部門のタスクの管理 |
| 全社のSkill公開者 | 全社のSkillの編集・公開 |
| 全社のタスク管理者 | 全社のタスクの管理 |
| 全件利用者（監査等） | `can_use_all_departments` |
| 全件管理者 | `can_manage_all_departments` ＋ 部門・全社のSkill・タスクのpermission |
| Connector管理者（技術者） | 共有のConnectorと接続のpermission |
| システム管理者 | システムのSkill・タスクのpermission |
| 連携の管理者（技術者） | 部門・全社・システムの出口、Slack・Teams等への接続のpermissionと、入口の一覧を見るpermission（Connector管理者が兼ねることが多い） |
| ユーザー管理者 | ユーザー、部門と所属のpermission |
| 基盤管理者 | `is_superuser`（すべてのpermissionを持つ人。非常口のログインとDjango管理画面） |

Connector管理者・連携の管理者・システム管理者・ユーザー管理者は、信頼された強い役割として割り切る。部門のタスク管理者は、部門のデータ（会話でも読めるもの）を、その部門に許された出口へ出せる役割として扱う。入口の鍵を外のサービスへ渡せることも、この役割に含める（§5.5）。例えばユーザー管理者は、アカウントを作り所属を決められるので、本質的にどの部門の人にもなれる（SSOが有効なら招待・再設定のリンクは使えず、この経路はパスワードのアカウントでだけ起きる）。

ここから、判定を3つの問いに分けて書く。

## 5 問い1：誰が定義を管理できるか

### 5.1 Skill

| 範囲 | 役割 | 見る・使う | Draftを変更する（本文・使うTool・資料・評価ケース） | 公開・切戻し・停止・削除・資料の検証の条件の変更 |
|---|---|---|---|---|
| 個人 | 個人の作業のやり方、試作 | 本人 | 本人 | 本人 |
| 部門 | 部門の正式な業務手順 | 使える部門 | 管理できる部門 ＋ `skill.can_edit_department_skills` | 管理できる部門 ＋ `skill.can_publish_department_skills` |
| 全社 | 全社員が使う共通の手順 | 全員 | `skill.can_edit_company_skills` | `skill.can_publish_company_skills` |
| システム | システムタスクの手順 | システム管理者 | `skill.can_edit_system_skills` | `skill.can_publish_system_skills` |

- 公開のpermissionはDraftの変更を含む。評価ケースの作成・変更・削除は編集の権限、「公開の前に必須」の印の付け外しと、必須のケースの変更・削除は公開の権限（編集の権限で公開の条件を緩められないように。design.md §3.7.1）。
- 機密のフラグ（design.md §4冒頭）を付けるのは編集の権限、外すのは公開の権限（編集の権限で機密の制限を緩められないように）。
- Skillが宣言するConnector（design.md §4.9.1）は使用の指示で、Runのアクセス範囲に関わらない。ただし宣言はSkillの中身の一部で、Skillの範囲の全員に見えるので、**Skillの範囲の全員に見えるConnectorだけを宣言して公開できる**（個人：本人が使えるもの。部門：その部門と全社。全社：全社。システム：システム・全部門・全社）。切戻しも同じ。これはSkillの中身に書けるものの規則で、エージェントは宣言と関係なくセッションの範囲のConnectorを使える。この規則により、**選べるSkillの宣言は、そのセッションで使える**（セッションの範囲はSkillの範囲を含むため。テストで確かめる）。公開の後にConnectorを止めた・移した等で使えなくなったら、Skillは選べ、操作を呼んだときにセッションの権限で断る。
- 範囲は通常の操作では変えない（必要なら新しく作る）。組織の再編での付け替えは §9。
- エージェントが会話からSkillを直すときも、依頼した人の権限で同じ判定をする。

### 5.2 Connector

| 範囲 | 役割 | 資格情報 | 見る・使う | 作成・編集・削除 |
|---|---|---|---|---|
| 個人 | 自分のファイル（OneDrive・Google Drive等）を読ませる | 本人のOAuthのtoken | 本人 | 本人 |
| 部門 | 部門の業務データ | 共有の資格情報 | 使える部門 | Connector管理者（`connector.add/change/delete_connector`） |
| 全社 | 全社員に見せてよい共通のデータ | 共有の資格情報 | 全員 | Connector管理者 |
| システム | システムタスクだけが使うデータ | 共有の資格情報 | `connector.view_connector` を持つ人（システム管理者・Connector管理者。定義だけ） | Connector管理者 |

- 接続（接続先と資格情報）は、permission（`connector.view/add/change/delete_<接続のModel>`）だけで判定する。
- 個人Connectorは、本人のtokenで読めるもの（本人に共有された他部門のファイルを含む）を読める。本人の権限を超えないので本人が作れる。外へ出す経路は §7で絞る。
- Connectorの範囲（どの表・列、どのサイト・フォルダ）はサーバー側で操作のたびに強制する。
- 管理画面での試し実行（SQLの実行）と、公開する表を選ぶための接続先の表の一覧は、接続先のデータを読むので編集の権限（`connector.change_connector`）で行う。見る権限（`connector.view_connector`）でできるのは、定義・表と列の説明・版の履歴まで。
- 会話向けのConnectorのAPI（`app/v1/connectors/`）は、使えるConnectorの公開する表の名前と説明・操作だけを返し、列の説明と接続先は返さない（Skillの編集画面で宣言するConnectorの候補にも使う）。システムのConnectorは会話では使わないので、見る権限を持つ人が範囲にシステムを指定したときだけ返す。画面は、候補をSkillの範囲で宣言できるものに絞る。

### 5.3 タスク

| 範囲 | 役割 | 定義を見る・作る・変える | チャットから起動する（印があるとき） |
|---|---|---|---|
| 個人 | 自分の作業の自動化 | 本人 | 本人 |
| 部門 | 部門の正式なワークフロー | 管理できる部門 ＋ `task.can_manage_department_tasks` | その部門に実際に所属する人、管理できる部門の人 |
| 全社 | 全社員に提供する共通の業務（弱い権限で済むもの） | `task.can_manage_company_tasks` | 全員 |
| システム | 強い資格情報が要る業務（複数の部門のデータの突き合わせ等） | `task.can_manage_system_tasks` | 不可 |

- 部門・全社・システムのタスクの定義（指示、使うもの、入口と出口）は、管理できる人だけに見せる。一覧も同じ規則で絞り、起動できる人には起動の候補として名前・説明・範囲と部門・今の版（と、起動のフォームに要る入力の項目の定義）だけを見せる。
- 「チャットから起動できる」の印は、版の外に持ち（停止と同じく、版を作らずに切り替える）、管理できる人が付ける。システムのタスクには付けない。印を外しても、起動済みのRunは止めない。起動した人が、Runに記録した範囲と部門のタスクを起動できる立場でなくなったとき（部門を離れた等）は、確かめ直すとき（§6）に止め、配信もしない。
- タスク単位の受付頻度・同時実行数の上限（design.md §9.3）も版の外に持ち、管理できる人が決める。上限に達している間は、起動できる人の本番の実行（入口・手動実行・チャットからの起動）を受付で断る。修正チャットの実行は数えず、断らない。
- 管理できる人なら誰でも直せる（1人の担当者に依存しない）。
- 管理できる人は、タスクの修正チャット（design.md §11.11）でタスクを動かし、会話で定義を直せる。修正チャットでは、停止中のタスクも動かせる（出口へ送らないため）。
- 横断の業務（全社Connector以外のデータが要る全社の業務）はシステムタスクにする。業務担当が要件と評価ケースを出し、システム管理者がConnector・入口・出口を決めて作る。

### 5.4 タスクのアクセス範囲と、定義で指示するもの

タスクの定義は、使うよう指示するSkillの版・Connector、モデル設定、出口、入力の形と制限を持つ。**タスクの定義にも版を持たせ**、Runは受付時のタスクの版に固定する（§6）。定義でSkill・Connectorを選ぶのは、エージェントに使うよう指示するためで、アクセス範囲を決めるためではない（§1の8）。

- **定義で指示するSkillは版を固定する**（ライブラリの依存と同じ）。Skillが新しい版を公開しても、タスクの指示は自動では切り替わらない。版を上げるのはタスクの変更で、タスクを管理できる人が差分を見て行う（画面で「新しい版があります」と知らせる）。エージェントが一覧から探して読み込むSkillは、会話と同じくその時点の最新の公開版を使う。
- **タスクのアクセス範囲**（タスクのRunが使えるものと、定義で指示できるもの）：

| タスクの範囲 | Skill | Connector | 入口・出口（定義で決める） |
|---|---|---|---|
| 個人 | 本人が使えるSkill | 本人が使えるConnector（個人Connectorを含む） | 本人のスケジュール、画面の通知、本人へのDM |
| 部門 | その部門の部門Skill、全社Skill | その部門の部門Connector、全社Connector | そのタスクの入口、その部門に許された出口 |
| 全社 | 全社Skill | 全社Connector | そのタスクの入口、全社に許された出口 |
| システム | システムSkill、部門Skill（どの部門も）、全社Skill | システムConnector、部門Connector（どの部門も）、全社Connector | そのタスクの入口、システムに許された出口 |

- 部門・全社・システムのタスクは、個人のSkill・Connector・入口・出口を使えない。
- **タスクのRunは、上の範囲にあるSkill・Connectorをすべて使える**。エージェントは、定義で指示されたものを使い、それ以外も会話と同じく一覧から探して使える。プロンプト・Skill・入力に何が書かれていても、この範囲は変わらない。
- 入力の制限：入力の項目ごとに、型と取りうる値（選べる対象）を決められる。
- Tool：タスクのRunのToolを、定義やSkillで絞らない。Skillの `tools` は手順が使うToolの宣言で、権限ではない（Sandboxは外のネットワークとConnectorの資格情報に届かず、Connectorは範囲と公開する表で守る）。外のデータを読み書きしない進行の制御のTool（業務結果を確定する `submit_result`、利用者に尋ねる `ask_user`、タスクの通知の書き方に従って完了の通知の文章と渡すファイルを決める `prepare_notification`）は、harness.md §7.5の条件（タスクに業務結果のSchemaがある、答える人がいる、タスクに通知の書き方がある）で加える。`prepare_notification` は出口・イベントを変えられず、渡すファイルも業務結果のファイルの項目の中から絞るだけ（design.md §4.3）。コードを実行する環境（Sandbox）は、Connectorの資格情報と外のネットワークに直接届かない。

### 5.5 入口と出口

入口（Trigger）と出口（配信先）は、管理する人を分ける。出口は、Connectorと同じく、部門・全社・システムのものは強い権限者（連携の管理者）が作る。Slack・Teams・Zapier等の外のサービスへデータを出す先になるため。入口は、起動するタスクを管理できる人が作る。入力の項目とpayloadとの対応を、業務を決める人が1人で決められるようにするため（§13）。

| 範囲 | 例 | 作る・変える人 |
|---|---|---|
| 個人 | 本人のスケジュール（入口）、画面の通知・本人へのDM（出口） | 本人 |
| 部門・全社・システムの入口 | スケジュール、Webhook | そのタスクを管理できる人（§5.3。入口のためのpermissionは足さない） |
| 部門・全社・システムの出口 | 画面の通知、Slack・Teamsのチャンネル、Zapier、Webhook | 連携の管理者（Django標準のpermission。所属は問わない） |

- 対話の連携（Teams・Slack等のスレッドで質問し、回答を受ける先）も出口として扱う。タスクの範囲に許されたものだけを選べ、質問・結果を投稿する直前にも、有効で範囲の中にあるかを確かめる。
- 部門・全社・システムの出口は、作るときに使ってよい範囲（どの部門・全社・システム）を決める。一度許したら、その範囲のタスクは自由に付けてよい（タスクごとの承認はしない）。
- **Webhookの入口が起動するタスクは1つだけ** にする。1つのタスクには複数の入口を付けられ、送り元ごとに入口を分ける（payloadの形が送り元ごとに違うので、payloadとの対応は入口ごとに持つ）。入口は、部門・全社・システムのタスクの画面で作り（タスクは入口なしで作れる）、範囲と部門はタスクと同じにする。1つの鍵で起動できるのは1つのタスクだけにする（鍵を持つ送り元が、後から付けたタスクまで起動できないように）。入口のタスクは作成時に決めて付け替えない。タスクを削除したら、そのタスクの入口をすべて論理削除する（鍵を使えなくし、受付の履歴と入口の版は残す）。結果の通知はタスクに1つなので、どの入口から起動したRunの結果も同じ出口へ届く。送り元ごとに届け先を分けたいときは、タスクを分ける（入口を足す画面に、結果の届け先を示す）。入口を停止しても、受け付けたRunは止めない（止めるときはタスクを停止する）。スケジュールの入口は、タスクごとに持つ。
- 出口を作る人は、実際の受信者（チャンネルの参加者、連携先の先）が許す範囲に合うかを確かめる。受信者の変更も、権限の変更と同じ重さで扱う。
- 入口を作る人は、Webhookの鍵を誰（どのサービス）に渡すかを確かめる。鍵を持つ送り元は「そのタスクが読めるものを、そのタスクの出口へ出させる」力を持つ。payloadの全体はデータとして作業場所に渡し（design.md §4.2）、その値で、タスクの範囲のConnectorの中で何を読むかが変わりうるが、これもこの力の範囲内として扱う。入口ごとに、送り元の認証（APIキー・署名）、重複の判定、取り出す項目（名前と場所）を決める（型と取りうる値はタスクの入力の項目で決める）。
- 鍵を最後に作った人を入口に記録する。その人がタスクを管理できなくなったら（部門を離れた等）、手元に鍵が残っているおそれがあるので、タスクの画面と入口の一覧に、鍵の作り直しを確かめる警告を出す。判定は表示のときに今の権限で行い、警告は鍵を作り直すと消える。自動では止めない（正規の送り元からの受付まで止めないため）。
- 入口の設定、受付の履歴（重複のキー、Runの状態）、Runの結果とログは、タスクを管理できる人がタスクの画面で見る。
- 発行済みの入口を見渡すために、一覧のAPIと画面（`/manage/trigger_bindings`）を置く。入口のModelの `view` のpermission（`task.view_triggerbinding`）を持つ人に、所属を問わず、入口の名前、タスクの名前・範囲と部門、鍵の先頭、停止中か、作った人と作った日時、鍵を作った人と日時、上の警告だけを見せる。見るだけで、作成・変更・停止・鍵の作り直しはできない。取り出しの設定、受付の履歴、タスクの定義は返さない。
- 出口としてのメールの送信は持たない（宛先を毎回変えられる送信は持ち出し口になりやすく、気軽に使われるため。招待のリンク等、システムから本人へ送るメールは出口ではなく、この規則の対象ではない）。必要ならZapierを出口にして、Zapier側で送る。
- **個人の出口は、画面の通知と本人へのDMだけ**にする。DMの宛先は本人に固定し、YorikiのアカウントとSlack・Teamsのユーザーの対応はメールアドレスの一致等で確かめたものを使う。Slack・Teamsへの接続（アプリ・bot）は連携の管理者が用意し、個人は接続を作らない。本人が作るWebhook等を出口に許すと、本人が読めるもの（本人に共有された他部門のファイルを含む）を自動で外へ流せるため、許さない。画面の通知は、個人のタスクで共通の出口を1つだけYorikiが作り、受け手は持ち主に固定する（design.md §4.4）。

## 6 問い2：このRunは誰の権限で動くか（実行許可）

Runを受け付けるときに、**実行許可**を組み立ててRunに固定する。実行許可は、誰の権限か（会話は依頼した人、タスクはタスクの範囲）、起動の種類、出口、入力の条件を持つ。使えるSkill・Connectorの一覧は持たず、その基準と各Skill・Connectorの範囲から、操作のたびに今の状態で判定する（§6.1）。

| 起動のしかた | 対象のタスク | 誰の権限 | 実行許可の中身 |
|---|---|---|---|
| 会話 | （タスクではない） | 依頼した人 | 依頼した人がアクセスできるSkill・Connectorすべて、利用者に許されたTool。出口は依頼した人への応答 |
| チャットからのタスクの起動 | 個人・部門・全社 | タスクの範囲（個人タスクは本人） | タスクの範囲でアクセスできるSkill・Connectorすべて（§5.4）。起動できるかは §5.3 で判定する。起動できる人はタスクより狭い権限を持たないので、操作のたびに「タスクの範囲 ∩ 起動した人の今の権限」で判定しても、タスクの範囲と同じになる（共通部分を取るのは、このことの検証を兼ねる。範囲ごとに同じになることをテストで確かめる） |
| 入口（スケジュール・Webhook） | 個人（スケジュールだけ）・部門・全社・システム | タスクの範囲（個人タスクは本人） | タスクの範囲でアクセスできるSkill・Connectorすべて（§5.4） |
| タスクの画面からの手動実行（個人・部門・全社は業務画面の `/tasks`、システムは管理画面） | 個人・部門・全社・システム | タスクの範囲（個人タスクは本人） | タスクの範囲でアクセスできるSkill・Connectorすべて（§5.4）。実行できるのはタスクを管理できる人（個人タスクは本人） |
| タスクの修正チャット（design.md §11.11） | 個人・部門・全社・システム | タスクの範囲（個人タスクは本人） | タスクの範囲でアクセスできるSkill・Connectorすべて（§5.4）。動かせるのはタスクを管理できる人で、追加の指示と回答を受け付ける。出口へは送らない。実行記録から始めるのは、その実行のログを見られて、今のタスクも管理できる人だけ。入力は元の実行のものを渡すので、元の実行かタスクの今の版のどちらかが機密なら修正チャットも機密にする。機密の修正チャットでは、タスクのRunは今の版のモデルがローカルLLMのときだけ動かす（再実行も同じ） |

- 「会話は依頼した人の権限で動く。タスクは、どの起動でもタスクの範囲で動く（個人タスクは本人の権限）」と整理する。チャットから起動できる人はタスクの範囲の人に限られ（§5.3）、起動のときに自由な指示を出せない。
- 修正チャットは、人が指示を出せるタスクのRun。指示を出せるのはタスクを管理できる人だけで、その人は依頼文を書き換えて手動実行できるので、指示を出せても力は増えない。出口へ送らないので、結果は管理できる人の画面にだけ出る。追加の指示と確認への回答は、修正チャットの持ち主（今もタスクを管理できる人）だけが出せる（ほかの管理者は、ほかのタスクのRunと同じく見る・止めるだけ）。実行中も区切りとConnectorの操作・Skillの読込みのたびに、動かした人が今もタスクを管理できるかを確かめ、できなくなれば止める（停止中かは見ないので、停止中に始めたRunは動く。停止の操作をしたときは、ほかのRunと同じくその時点のRunに停止を依頼する。削除は見る）。
- タスクの編集のRun（design.md §11.11）は会話のRunで、依頼した人の権限で動き、ほかの会話のRunと同じくSkill・Connectorを使える。タスクの定義を変えるToolは、依頼した人がそのタスクを管理できるかを呼ぶたびに確かめる。直せるのは依頼文・通知の書き方・入力の項目の説明だけで、使うもの（Skill・Connector・出口・モデル）は画面でだけ変える。
- 個人タスクはどの起動でも本人の権限で動く。入口からの起動で個人Connectorの本人のtoken（refresh token）を使うのは、本人がそのタスクの無人実行を明示的に有効にしたときだけ。tokenの失効、本人の無効化で止まり、再認可の手段を用意する。
- **サブエージェント**（harness.md §10.11）は親の実行許可の範囲で動く（親と同じ人の権限で、Skillの変更はできない）。モデルもagentセッションで使えるものに限る（機密ならローカルLLM）。
- **タスクのRunは、会話の文脈を引き継がない**。チャットから起動しても、文脈はタスクの定義と入力だけで組み立てる（会話に残った、もう使えない部門の情報をタスクの出口へ流させないため）。
- **人のいない起動は、指示を受け取らない**。対話の連携（Teams・Slack等のスレッド）があっても、チャネルの参加者ができるのは、エージェントが尋ねた質問への回答と停止だけで、追加指示は受け付けない。回答は質問への答えとしてだけ取り込み、実行許可は変わらない。
- 人が起動したRunでも、スレッドから追加指示を出せるのは、そのRunを起動した本人（Yorikiのアカウントに紐付いた人）だけ。ほかの参加者は回答と停止だけ（起動した人の権限で、ほかの人の指示を実行しないため）。
- 入口と手動実行で受け取るのは、タスクの定義で型を決めた入力（項目・値・ファイル）だけで、自由な依頼文は受けない。指示はタスクの定義（プロンプト・Skill）にだけある。チャットからの起動も、手動実行と同じく型を決めた入力だけを受け取る（会話の文章は渡さない。タスクを動かしながら指示を出して直す場面は、タスクの修正チャットで扱う。上の表）。
- 会話のTool：利用者に許されたToolを使う。会話を開始したユーザーがアクセスできるものはすべて使え、Skill（`/`）・Connector（`@`）の指定は使用の指示で、アクセス範囲を広げも狭めもしない（§1の8）。将来、会話に外へ出すTool（メールの送信等）を足すときは、利用者本人の送信の権限で動かし、宛先をRunの中で確定する。Skillが送信の権限を与えることはない。
- **再実行とリトライ**：
  - 再実行（利用者・管理者が「もう一度」を選ぶ）は、今のタスクの定義で新しいRunを作り、入力だけを引き継ぐ。実行許可は今の権限で組み立て直す。
  - リトライ（障害からの自動の再試行）は、同じRunの続きとして元の実行許可で行う。定義で指示したSkill・Connectorや出口が停止・削除・範囲の変更で外れていたら、リトライせずに失敗にする。
  - キューで待っているRunは、受付時のタスクの版のまま動く（会話の「Runの中では固定」と同じ）。タスクの定義を直しても、待っているRunは失敗させない。止めたいときはタスクを停止し、停止は待っているRunにも効く。
  - 出口への配信は、Run・出口・送る項目ごとの安定したIDで重複を防ぎ、連携先に重複を防ぐ仕組みがあれば使う。送ったかどうか分からない障害では、自動で送り直さず、確認待ちにする。
- **確かめ直すとき**：受付時、キューから実行を始めるとき、出口への配信・外への送信の直前に、タスクが停止されていないか、定義で指示したSkill・Connectorと出口が今も有効で範囲の中にあるか、起動した人が今も有効で起動できる立場か、個人タスクの本人が今も有効で権限を持つかを確かめ、外れていれば実行・配信しない。実行中に権限が変わったら、次のConnectorの操作から効く。長く動くRunは、管理者が取り消せる。
  - 実行中に確かめ直すときの範囲・部門は、Runに記録したものではなく今のタスクのものを使う（範囲は変わらず、部門の付け替えは組織の再編の操作のため）。
  - 出口への配信の直前には、タスクの停止・削除、部門のタスクの部門の無効化、個人のタスクの持ち主の無効化も確かめ、どれかに当たれば送らずに取消にする（停止で止めたRunの `run.cancelled` も、停止中は送らない）。
  - 「起動した人」を確かめるのは、チャットからの起動（結果を受け取る人なので、起動できる立場かを確かめる）だけ。手動実行のRunはタスクの範囲の権限で動くので、手動実行した人の今の権限は、実行中にも配信の直前にも確かめない（「本人」は個人のタスクの持ち主）。
  - タスクの定義の保存（画面のAPIと `update_task`）は、保存の後に同じtransactionの中で権限を確かめ直すが、権限の剥奪とは完全には直列にしない（剥奪と同時の保存は通りうる）。
- Runには、実行許可、起動のきっかけ（起動した人・入口と送り元）、最後にタスクを保存した人、固定した版と入力を記録する。手動実行・チャットからの起動のRunの実行主体（`Run.owner`）は起動した人にする。入口からの起動のRunの実行主体は、ログインできないシステム用のユーザー（`is_system`。1人だけで、パスワードを持たない）にする（利用量の記録と名前に使い、権限の判定には使わない）。入口と送り元は受付の記録（TriggerReceipt）に残す。

### 6.1 Runと会話（固定はRunの中だけ）

- 会話の1つのRunは、親が動き始めてから、親が動き終え、ジョブとサブエージェントがなくなるまでのひとまとまり（design.md §5.1。話の区切りではなく、複数の依頼が混ざりうる。0.47の形で、実装はこれから）。実行中の発言、確認待ちからの再開、障害からの試行（Attempt）も同じRunの中。
- 固定は**Runの中だけ**で、固定するのはモデル設定（利用者が明示して切り替えれば実行中のRunも切り替わる。design.md §4.8）、タスクのRunの実行許可と版、読み込んだSkillの版。Runが使えるSkill・Connectorは固定せず、会話は依頼した人の今の権限、タスクはタスクの範囲で判定する。読めるものは読み、作業中の発言で `/`・`@` を指定すれば、その時点の権限で、Skillは最新の公開版を読み込む（design.md §3.2、harness.md §10.1・§10.2。読み込むときにセッションの権限で選べるかを確かめ、読み込んだ時点を記録する。すでに読み込んだSkillを指定すれば切り替わる）。会話をまたいでは固定しない。会話は何日も続き、その間の異動・権限の変更・Skillの改善を反映するため。
- 会話は文脈を引き継ぐので、次のことが起きる。
  - 前に読んだSkillの古い版が文脈に残る。新しい版を読み込むときは、前に読んだ版に代わるものであることをモデルに明示する。
  - 権限を失った後も、前のRunで読んだデータ（Connectorの結果等）は文脈とWorkspace（`/workspace/work`・`/workspace/output`、Connectorの結果のファイル）に残り、次のRunのエージェントも読める。どちらも本人の会話のもので、本人が見る・取り出すことができたものなので、**許容する**（文脈から外すことも、Workspaceの復元を止めることもしない）。ただし、使えなくなったConnectorはもう呼べない。タスクのRunは、会話の文脈もWorkspaceも引き継がない。

## 7 問い3：このRunは何を読み、どこへ出せるか

- 読めるもの：実行許可の基準（§6）でアクセスできるSkill・Connector。Connectorの範囲と公開する表は操作のたびに強制する。
- 出せる先：

| 出す経路 | 規則 |
|---|---|
| 会話の応答 | 依頼した人に返す（その人が使えるものだけで作った結果なので、その人に見せてよい）。チャットから起動したタスクの結果は、起動した人に返す（タスクの範囲で作った結果で、起動できるのは §5.3 の範囲の人だけ） |
| タスクの出口 | 実行許可の出口だけ（§5.4でタスクの範囲に許されたものに限っている） |
| 書込み（書込みのConnector等） | 今は未実装だが、対応する。**書込みも出口として扱う**。書込み先はタスクに許されたもの（タスクの範囲に含まれるもの）だけで、対象を限定して明示的に許可する。部門のデータを全社の書込み先へ保存して、出口を通さずに広げることはできない |

- 部門タスクが部門のデータを全社向けの出口へ流すことはできない（出口の範囲で塞ぐ）。全社へ出す必要がある業務は、システムタスクとして作る。
- 個人タスクの出口は、画面の通知と本人へのDMに限る。
- **機密の区分**（design.md §4冒頭）：機密のConnectorと機密のSkill（機密のフラグを付けたSkill）は、機密（個人情報・機密情報を扱う）の会話・タスクのRunでだけ読める。機密の会話・タスクはローカルLLMのモデルだけを使い、会話は途中から機密にできるが非機密には戻せない。機密の会話・タスクの結果は、機密の結果を送ってよいとした出口にだけ出す（出口の機密のフラグ）。ただし画面の通知は、フラグがなくても使える。認証の要る画面の中だけで、受け手をRunの結果を見られる人（§7.1。送った後に見られなくなった人には見せない）に限って見せるため（見せるのはタスクの名前とRunの状態と、通知の書き方に従ってエージェントが決めた通知の文章。文章は業務結果から作るので機密の情報を含みうるが、受け手はもともとそのRunの結果を見られる人だけ。design.md §4.3・§4.4）。範囲・所属による判定とは別の軸で、両方を満たすときだけ読める・出せる。

### 7.1 Runの結果とログを見られる人

ログ（Toolの呼出しと結果、内部の記録、エラー、入力）を見られるのは、そのものを管理できる人だけ。結果（最後の応答、業務結果、成果物）とログは分けて持つ。

Runには、実行したときのタスクの範囲と部門を記録し、結果・ログ・成果物を見られるかは、タスクの今の範囲ではなくこの記録で判定する（タスクを別の部門・全社へ移しても、移す前のRunは、移す前の範囲を管理できる人だけが見られる）。

Runの中身が外へ出る経路をすべて列挙し、どれにも「結果」か「ログ」の判定を当てる：一覧・詳細のAPI、検索、SSE（実行中の進み具合）、RunEvent、エラーの本文、添付・成果物のダウンロードと期限付きURL、出口への配信の履歴、Webhookの送り元が状態を確かめる口（状態と決まった失敗のコードだけを返し、エラーの本文やログ由来の情報は返さない）。社員向けのダウンロードには期限付きのtokenを使わず、セッションで認証して、取得するたびに結果を見られるかを判定し直す（異動や権限の取り消しが、発行済みのURLにも効くように）。期限付きURL（APIのtoken）は、出口（Zapier等）へ渡すものだけに使い、対象のファイルと短い期限に限る。S3の署名付きURLを直接渡さず、取得のたびにAPIが、tokenと出口が有効か、出口がまだそのRunのタスクの範囲に許されているかを確かめてから、ごく短い期限の署名付きURLへリダイレクトする。出口を止めた・消した・タスクの範囲から外したら、その出口へ渡した未使用のtokenも失効させる。

チャットから起動した人は、起動した後に権限を失っても、自分が起動したRunの結果は見られる（ログは見られない）。起動した人に見せる結果は、状態と終わり方、自分の入力、最後の応答、業務結果、成果物で、失敗の理由の本文（プロバイダのエラー文等を含みうる）、最初の依頼（タスクの依頼文から作るので定義の一部）とモデル設定、作業の記録（Skillのスクリプトからの Connectorの呼出しを含む）と作業の計画、使ったSkill、入力の添付とConnectorの結果、配信の履歴、実行中の進み具合（SSE）はログとして見せない。起動した会話には、Runを指すカード（状態と最後の応答）を出すが、カードは会話のRunの文脈に入れない（タスクの結果を会話のモデルへ渡さない）。起動した人は、自分が起動したRunを止められる。実行中に権限を失えば、その後のConnectorの操作は断られるので、結果に入るのは権限を持っていた間に読んだものだけで、会話の文脈とWorkspaceに残るのと同じ扱いになる（§6.1）。

修正チャット（design.md §11.11）のタスクのRunの作業の記録（最初の依頼、追加の指示、応答を含む）はログなので、ほかのタスクのRunと同じく、実行したときの範囲を管理できる人だけが見る（タスクを削除した後も見られる）。修正チャットの持ち物で、本番の実行の一覧には出さず、修正チャットの削除とともに消える。修正チャットの持ち主が管理できなくなったら、修正チャットの中のタスクのRunの記録は見せない（持ち主は、管理できなくなった後も修正チャットを削除でき、そのとき動いているRunにも停止を依頼する。そのRunは次の区切りで止まるので、権限は広がらない）。タスクを動かすこと・追加の指示・回答・編集の依頼は、今のタスクを管理できる人だけが出せる（編集のRunの文脈には、タスクのRunの記録が入るため）。添付と成果物、それまでの編集のRunの応答は、会話のものとして残る（その人が管理していた間に見られたもので、§6.1と同じく許容する）。

| Run | 結果 | ログ |
|---|---|---|
| 会話 | 依頼した人 | 依頼した人（本人の会話なので本人が管理する） |
| 個人タスク | 本人 | 本人 |
| 部門・全社タスク（チャットから起動） | 起動した人とタスクを管理できる人 | タスクを管理できる人（起動した人の入力・添付を含む。部門・全社のタスクは正式なワークフローなので、管理者が不具合を調べられるようにする。起動する前に、入力と処理の記録をタスクの管理者が見られることを起動した人に示す） |
| 部門・全社タスク（入口・手動実行） | タスクを管理できる人（出口へ届けたものは出口の受信者） | タスクを管理できる人 |
| タスク（修正チャット） | タスクを管理できる人。修正チャットの持ち主は、管理できなくなった後も、修正チャットの添付と成果物は見られる | タスクを管理できる人 |
| システムタスク | システムタスクを管理できる人（出口へ届けたものは出口の受信者） | システムタスクを管理できる人だけ |

### 7.2 実装の形

権限の判定は、規則がずれないように集め、効率よく絞る。

- **所属の判定**は、`user`の関数（使える部門・管理できる部門と、部門タスクのチャットからの起動に使う実際の所属）だけで行う。ほかの場所では所属を直接引かない。リクエストの中で1回だけ計算して`request.user`に持たせる（permissionはDjangoがユーザーごとにキャッシュしている）。キャッシュは読むだけに使い、権限・所属を変える処理の後では使わない。Workerはユーザーの情報を使い回さず、確かめ直すたびにDBから読む。停止と外への送信がぶつかる場面は、行ロックと冪等のIDで扱う。
- **ものごとの判定**は、各アプリのQuerySetとModelに置き、Viewには書かない。
  - 一覧の絞り込み：`<Model>.objects.visible_to(user)`・`manageable_by(user)`。
  - 1件の判定：`obj.can(user, 操作)`。操作は「見る・使う・管理・起動・結果を見る・ログを見る・候補に出す」を区別する（`access_of(user)` 1つでは操作の違いを表せない）。
  - 範囲ごとに「誰が見る・使う・変えるか」を1つの規則表に書き、QuerySetとModelの両方がそれを読む。
  - Viewは`get_queryset`でQuerySetの絞り込みを使い、操作ではModelの判定を呼ぶだけ。一覧では隠れるのにIDを指定すると読める、という食い違いを構造で防ぐ。
  - Serializerの関連の項目（Connector・Skill・出口のID）の選択肢も同じ判定で絞り、保存の直前にも確かめる（画面に出ないIDを登録させない）。
  - Worker（Django Q2）や管理コマンドでも、`request`に頼らず同じ判定を呼ぶ。Q2にはIDだけを渡し、WorkerがDBからRunと実行許可を読み直して判定する。
  - 一覧（QuerySet）と1件の判定が同じ結果になることを、操作ごとにテストで保証する。
- **一覧の効率**：部門のID・範囲・持ち主・有効の条件でSQLで絞り、1件ずつ判定しない。これらの列に索引を置く。
- **実行許可の保存**：Runには、誰の権限か・起動の種類・タスクの版・固定した版（読み込んだSkill・モデル設定）だけを保存し、操作のたびに対象だけを判定する。使えるもの全件の一覧は持たない。Runがエージェントに見せるSkill・Connectorの一覧は、Run開始時と発言を取り込むたびに今の権限（タスクはタスクの範囲）で作り直す（harness.md §10.1・§10.2）。
- **参照先の版**：Connectorの変更（対象の列等）は、タスクの版が同じでもすぐ効く（管理者の責任）。Runには使ったConnectorの版を記録する。出口は、Runに版を固定し、Runの途中で新しい宛先へ自動で向けない（宛先を変えた後の配信が、確かめていない先へ飛ばないように）。出口が停止・削除・タスクの範囲の外になったら、配信の直前に確かめて送らない。機密の結果を送れるかは、Runに固定した版と出口の今の版の両方で確かめ、どちらかが許さなければ送らない。
- **候補のAPIと設定のAPIを分ける**：タスク・Skillの編集画面で選ぶ候補（Skill・Connector・出口）は、ID・名前・用途・範囲だけを返す専用のAPIにし、資格情報や接続の設定を返すAPIとは分ける。タスクの編集画面の候補は、範囲（と部門）を指定して、その範囲のタスクが使えるものだけを返す（Skill：`app/v1/tasks/skill_choices/`、Connector：`app/v1/tasks/connector_choices/`、出口：`app/v1/destinations/`）。登録できるかの規則は保存のときの検査と同じもの（`task/checks.py` の `skill_allowed()`・`connector_allowed()` と、同じ規則のSQLの `allowed_skills()`・`allowed_connectors()`）を使い、その範囲のタスクを管理できない人には403を返す（Skillの候補は、固定できる版の番号も返す）。
- **テスト**：superuserでは判定のテストをしない（存在しないpermissionの名前でも通り、書き間違いを隠すため）。必要なpermissionだけを付けたユーザーで試す。一覧で件数が増えてもクエリの数が増えないことも確かめる。すべての役割の組み合わせではなく、境界ごとに重点を置く（範囲ごとの見る・使う・変える、一覧・詳細・Runの履歴で判定が同じか、許された読取りから許されない出口への流れ、定義の変更後のリトライ、待っているRunとタスクの停止）。

### 7.3 画面

画面は層で分ける。業務画面は「自分の所属から見える」場所、管理画面は「所属を問わず、すべてを扱う」場所。

| 層 | 画面 |
|---|---|
| 利用・業務の管理 | 業務画面（ルート直下）。同じ画面の中で、できることに応じて編集・公開のボタンが出る |
| 基盤の管理 | 管理画面（`/manage`）。一覧は所属で絞らず、permissionだけで決まる |

- `/manage`の入口は、管理画面のメニューに出せる項目があるときだけ出る（基盤の管理のpermissionを持つ人だけ）。部門のSkillの公開者・部門のタスク管理者は管理画面に入らない。
- 会話の`/`・`@`の候補は、業務画面の「使える」一覧と同じQuerySetから作る。

| もの | 業務画面 | 管理画面 |
|---|---|---|
| Skill | `/skills`：個人・部門・全社 | システムSkill（`/manage/system_skills`。Skillの編集の部品を使い回す） |
| Connector | `/connectors`（使えるConnectorを見る、個人Connector。個人Connectorの段階で作る。今は会話の `@` の一覧で見る） | `/manage/connectors`：部門・全社・システム（全件） |
| 接続先 | — | `/manage/database_connections` |
| タスク | `/tasks`：個人・部門・全社 | システムタスク（`/manage/system_tasks`） |
| 入口 | タスクの画面で作り、変える（システムのタスクも同じ画面を使う） | 入口の一覧（見るだけ） |
| 出口 | 個人の出口（画面の通知・本人へのDM）はタスクの編集の中で選ぶ | 部門・全社・システムの出口 |
| Runの結果・ログ | 会話の画面（本人）、タスクのRunの画面（`/tasks/{task}/runs/{run}`。管理できる人・結果を見られる人。画面の通知からも開く）、タスクをまたいだ実行の履歴（`/runs`。本番の実行のうち結果を見られるもの。修正チャットのRunは出さない。design.md §11.9） | システムタスクも同じタスクのRunの画面 |
| ユーザー・部門・SSO・LLM・Runtime Profile | — | `/manage` |
| 基盤の設定（ワークスペースの保存期限。design.md §8） | — | `/manage/settings`（`runtime.*_platformsettings`。Groupは作らず、基盤管理者が扱う） |
| 予算（design.md §9.1・§9.2・§9.4） | `/usage`：所属している部門と管理できる部門、全社・システムのタスクを管理できる人と所属のない人にはシステムの枠の、今月の利用額・上限・残額と、実行回数・同時実行数とその上限（見るだけ） | `/manage/budgets`：既定の上限（金額・月の実行回数・同時実行数・Runごとの金額）、部門ごとの上書き、全部門とシステムの枠の今月の利用額・実行回数・同時実行数（`usage.*_budget`） |

#### 7.3.1 業務画面の一覧（Skill・タスク共通の形）

範囲で絞った一覧から、選んで詳細（編集）に入る。

```
[すべて] [個人] [部門 ▼経理部] [全社]        □ 編集できるものだけ      [＋ 作成]
──────────────────────────────────────────
請求書の照合   部門・経理部   公開中 版5   編集・公開できます
名寄せ         個人           公開中 版2   編集・公開できます
議事録の要約   全社           公開中 版8   使えます
```

- 範囲のタブ：すべて（既定）・個人・部門・全社。システムは出さない。
- 業務画面のメニューの「タスク」は全員に出す（個人のタスクは誰でも作れるため）。
- 部門の選択肢は、Skillは`usableDepartments`、タスクは`manageableDepartments`。
- 行ごとの「できること」は、サーバーが判定した可否を出す。
- 作成ボタンは作れる範囲があるときだけ出す（個人はいつでも、部門は`manageableDepartments`と部門の編集・管理のpermission、全社は全社のpermission）。作成の画面で選べる範囲と部門も同じ規則で絞る。

| | Skill（`/skills`） | タスク（`/tasks`） |
|---|---|---|
| 一覧に出るもの | 使えるもの全部 | 管理できるものだけ（定義は管理できる人だけに見せる） |
| 「編集できるものだけ」 | 要る | 要らない |

- チャットから起動できるタスクは、`/tasks`には出さず、会話の入力欄の候補として出す。

## 8 信頼しない入力とプロンプトインジェクション

信頼しない入力：Webhookのpayload、添付・読み込む文書（PDF・Office・CSV等）、Connector・Toolの結果、Webから取得したもの。

- **守りは制約で行う**：信頼しない入力に何が書かれていても、実行許可（範囲・Tool・出口）は変わらない。入力に誘導されても、届くのはタスクの範囲の中のSkill・Connector（公開する表の中。今は読取りだけ）だけで、出せる先はタスクの出口だけ。モデルへの指示と信頼しない内容の区切りでは完全には防げず、Webhookの鍵を破られた場合も防げないので、被害はこの範囲と出口の中に収まるものとして割り切る。書込みのConnectorを入れた後は、書込み先もこの範囲に入る（§7）。Skillの公開・変更、出口の変更、権限の変更をするToolは、タスクのRunには渡さない。出口の宛先は出口の定義で決まり、入力からは変えられない。
- 指示ではない入力でも、許された操作の中で誘導はできる（Webhookの値を検索の条件にして大量に取得する等）。これは入力の型と取りうる値（§5.4）と、Connectorの取得件数の上限で抑える。
- **補助**：信頼しない入力は、モデルに渡すときに区切って「データ」であることを明示する。
- **後で足せる補助**：入力に指示が含まれるかを判定する仕組み（ガード用のモデル等）。誤検知と見逃しがあり、判定するモデル自体もだまされうるので、止めるためではなく記録と通知のために使う（出口・書込みのあるタスクで、信頼しない入力だけを判定し、疑わしいものを管理者へ知らせる）。入れなくても設計は変わらない。
- 会話で社員が添付した文書も同じ扱い。添付の中の「Skillを書き換えよ」等を、利用者の依頼として扱わない。

## 9 部門の再編と削除

- 部門は削除せず、無効にする。無効にした部門のもの（Skill・Connector・タスク・入口・出口）は新しく使えず、タスクは起動しない。所属・Runの履歴は残す。
- 部門のSkill・Connector・タスク・出口を別の部門・全社へ移す操作は、組織の再編のための別の操作とする（基盤の管理）。入口は単独では移さず、タスクと一緒に移る（範囲と部門をタスクと同じに保つため）。移す前に、影響（使えるようになる人、そのものを使うタスク、出口の受信者）を表示して確認させる。過去のRunの結果・ログは移した先へは見せない（§7.1。実行したときの範囲と部門で判定する）。移す間は、それを使うタスクを止め、移った先で有効にし直す。

## 10 基盤の管理

- 管理APIはすべてpermissionで判定する。対象：部門・全社・システムのConnector・出口、接続、入口の一覧、システムのSkill・タスク、LLMの接続・モデル設定、Runtime Profile、基盤の設定（ワークスペースの保存期限。design.md §8）、予算（金額・月の実行回数・同時実行数の、既定の上限と部門ごとの上書き、Runごとの金額の上限。design.md §9.1・§9.2・§9.4）、SSOの設定、ユーザー（招待のリンクの発行を含む）、Groupの一覧（割り当ての選択肢）、部門と所属。Django標準のpermission（view・add・change・delete。changeを持てばviewもできる）か、範囲ごとのpermissionを使う。追加・削除だけを任せることはせず、add・deleteはviewかchangeと一緒に付ける（一覧を見られないと、任せた操作にたどり着けないため）。
- permissionの指定を書き忘れた操作を閉じる既定（`DEFAULT_PERMISSION_CLASSES`）は、誰も通さないものにする（superuserも通さない。書き忘れはテストですぐ分かる）。`PlatformAdmin`はなくす。
- 委任したときの防止策（強い役割の中での事故を減らすためのもの）：
  - ユーザーの更新APIで書ける項目は、表示名・有効・Group・所属だけ。permissionの直接付与、`is_superuser`、SSOの識別子はAPIに出さない。
  - 自分の所属・Groupは変えられない。
  - 部門の画面での所属の付け外しにも、ユーザーの更新と同じ防止策を当てる（自分の所属は変えられない。自分の持たないpermissionを持つアカウントの所属は変えられない）。
  - 自分の持たないpermissionを含むGroupは、誰にも付け外しできない。
  - 基盤管理者のアカウントは、基盤管理者だけが変更・リンクの発行をできる（permissionの比較とは別に判定する。§4.1）。
  - 自分の持たないpermissionを持つアカウントは、変更も招待・再設定のリンクの発行もできない。発行は記録する。リンクを使うとき（受け入れのとき）にも、発行した人が今も有効で、対象のpermissionが発行した人の今のpermissionに含まれるかを確かめ、外れていればリンクを使えなくする（発行の後に発行した人が権限を失った、対象が昇格した場合に、残ったリンクでアカウントを乗っ取らせない）。画面には、操作する人から見た可否（`can_change`・`can_issue_invitation`）をサーバーが返す。
  - Groupの中身の編集はDjango管理画面（基盤管理者だけ）。

## 11 初期のGroup

最初に一度だけ作る。後から名前・中身を変えても、消しても、作り直さない。後の段階で足すpermission（タスク等）は、その段階のマイグレーションで一度だけ、新しいGroupを作るか既にあるGroupに足す（消したGroupは作り直さない）。

| Group | permission |
|---|---|
| 部門のSkill編集者 | `skill.can_edit_department_skills` |
| 部門のSkill公開者 | `skill.can_edit_department_skills`、`skill.can_publish_department_skills` |
| 全社のSkill公開者 | `skill.can_edit_company_skills`、`skill.can_publish_company_skills` |
| 部門のタスク管理者 | `task.can_manage_department_tasks` |
| 全社のタスク管理者 | `task.can_manage_company_tasks` |
| 全件利用者 | `user.can_use_all_departments` |
| 全件管理者 | `user.can_manage_all_departments`と、部門・全社のSkill・タスクのpermission |
| Connector管理者 | `connector.*_connector`、`connector.*_<接続のModel>` |
| システム管理者 | `skill.can_edit_system_skills`、`skill.can_publish_system_skills`、`task.can_manage_system_tasks`、`connector.view_connector`（システムタスクに登録するConnectorの定義を見るため） |
| 連携の管理者 | 出口のModelのpermission（`delivery.*_destination`。配信の段階のマイグレーションで足した）と、入口の一覧を見るpermission（`task.view_triggerbinding`） |
| ユーザー管理者 | `user.*_user`、`user.*_department` |
| 予算の管理者 | `usage.view_budget`・`usage.change_budget`（金額・月の実行回数・同時実行数の、既定の上限と部門ごとの上書き、Runごとの金額の上限。予算の段階のマイグレーションで足した） |

## 12 0.33で変えたこと（以前の設計・実装から）

- Skill：部門の中の役割（利用・編集・公開）をやめ、部門の範囲を所属とpermissionで判定する。部門は1つ（今のまま）。システムの範囲を足す。
- Connector：使える部門（多対多、空なら全社向け）をやめ、範囲（個人・部門・全社・システム）と1つの部門にする。作成・編集は所属を問わずpermissionだけにする。
- 部門の「すべての部門の範囲を含む」印をやめ、`can_use_all_departments`・`can_manage_all_departments`と、使える部門・管理できる部門の2つの関数にする。
- 初期のGroupを`migrate`のたびに作り直す仕組みをやめ、最初に一度だけ作る。
- 基盤管理者だけにしていた管理APIを、すべてpermissionにする。`PlatformAdmin`をなくし、既定は誰も通さないものにする。
- フロントエンドに渡している`is_platform_admin`をなくす。
- 移行：消して困るDBのデータはないので、今のデータを新しい形に置き換え、合わないもの（複数の部門を持つConnector、部門の中の役割、「すべての部門」の印）は消すか作り直す。
- 設計書では、タスクがSkillの「最新の公開版」を使える。これをやめ、タスクでは版を固定する。会話では今までどおり最新の公開版を使う。
- 設計書の「Webhookで起動したRunの実行主体はタスクに設定した社員」（0.31）をやめ、§6の実行許可の形にする。
- 入口（Trigger）・出口（配信先）に範囲を持たせ、部門・全社・システムのものは連携の管理者が作る。個人の出口は画面の通知と本人へのDMだけ。出口としてのメールの送信は持たない。
- タスクの定義に版を持たせ、Runは受付時の版に固定する。

## 13 design.md 0.45で変えたこと

- 入口（Webhook）を作る・変える人を、連携の管理者から、そのタスクを管理できる人へ移す。入力の項目はタスク、payloadとの対応は入口が持つ形のままで、業務の変数とその取り出しを別の人が決める調整をなくすため。入口のためのpermissionは足さない。
- 鍵を外へ渡せるようになる人は増えるが、鍵を持つ送り元の力の上限は変わらない。読めるのはタスクの範囲の中で（§5.4）、送れるのは連携の管理者が用意した出口だけ。
- 鍵を作った人がタスクを管理できなくなったら、鍵の作り直しを確かめる警告を出す（§5.5）。既存の入口は鍵を作り直した人の記録がないので、鍵を作った人を空にして移し、誰の手元に鍵があるか分からないものとして、鍵を作り直すまで警告を出す。
- 1つのタスクに複数の入口を付けられるようにする（入口が起動するタスクは1つのまま）。
- 連携の管理者のGroupから `task.add_triggerbinding`・`change_triggerbinding`・`delete_triggerbinding` を外し、`view_triggerbinding` で一覧だけを見る形にする。

## 14 design.md 0.51で変えたこと

- 利用できることと、使うよう指示することを分けた（§1の8）。会話の `/`・`@`、タスクの定義で選ぶSkill・Connector、Skillの宣言と `tools` は使用の指示で、アクセス範囲を決めない。
- タスクのRunが使えるものを、「タスクに固定したもの」から「タスクの範囲でアクセスできるものすべて」にした（§5.4）。以前の「タスクに登録できるもの」の表を、そのままタスクのアクセス範囲とする。エージェントは一覧から探して使える。
- ToolをSkillの `tools` で絞るのをやめた（タスク・Draftの評価のRunを含む）。タスクごとのConnectorの取得件数の上限とToolの引数の制限（未実装）はなくす。
- チャットから起動したタスクも、タスクの範囲で動く。起動した人の権限との共通部分は取り続けるが、起動できる人（§5.3）はタスクより狭い権限を持たないので、タスクの範囲と同じになる（テストで確かめる）。
- 書込みのConnectorは、今は未実装だが対応する（§7）。
- システムのタスクは、Skillもシステム・全部門・全社を使える。
- 宣言できるConnectorをSkillの範囲で決める（§5.1）。
- Skillについて権限が決めるのは、セッションの権限で選べるかだけにした（§1の8）。公開の後に使えなくなった宣言は、Connectorの操作のときに断る。読み込んだSkillが停止・失効してもRunは止めず、新しく選べなくなるだけ。必要な能力は案内だけで、モデルの選択を制限しない。機密のSkillはSkill自身のフラグだけで決める。使うToolの変更は編集の権限にした。修正チャットでも、セッションの権限で選べる `/`・`@` を受け付ける。
