# Sandboxの設計の新案

Sandboxのイメージと、ワークスペースの扱いを見直す案。まだ採用しておらず、今の仕様は design.md・harness.md・sandbox/CONTRACT.md を正とする。採用したら、中身をそれらへ移して本書を消す。

各項目の印の意味：

- **合意**：利用者と決めたこと
- **案**：提案で、まだ決めていないこと
- **未決**：これから議論すること

---

## 1 目的

- 1つのイメージで、文書処理を一通り動かせるようにする（**合意**）。`SKILL.md` の形の外部のSkill（docx・pptx・xlsx・pdf等）に必要な道具も、ここに含める。
- 「リッチ」は、この「1つのイメージで一通り動く」ことを指す。道具ごとに機能を削らないという意味ではなく、各道具はSkillで使う最低限にする（**合意**）。
- 外部のSkillはイメージにもYorikiにも同梱しない。導入先が公開されているものを取り込み、取り込むかどうかの判断も導入先が行う（**合意**。取り込みの仕様は本書の範囲の外）。

## 2 イメージの構成

イメージは今の `yoriki-sandbox-docs` の1つのまま、次を足す。軽いイメージと文書用のイメージには分けない（**合意**）。今の大きさは582MB。足した後の大きさは、ビルドして測る。

| 種類 | 内容 | 状態 | 今のイメージ |
|---|---|---|---|
| LibreOffice | ヘッドレスで、Writer・Calc・Impressの変換と計算に要るものだけ | **合意** | なし |
| Node.js | 本体と、スキルが使うパッケージ（`docx`、`pptxgenjs`、`react`、`react-dom`、`react-icons`、`sharp`） | **案** | なし |
| 変換の道具 | pandoc、poppler-utils（`pdftoppm`） | **案** | なし |
| Python | `markitdown` を足す | **案** | ほかの `openpyxl`・`pandas`・`pypdf`・`pdfplumber`・`python-docx`・`python-pptx`・`pillow` 等はある |

パッケージの一覧は、公開されているスキルの説明を検索して拾ったもので、すべての依存を確かめたものではない。作るときに現物で確かめる。

- Sandboxにネットワークがないのは変えない。`npm install` はできないので、Node.jsのパッケージはPythonと同じく、版とhashを固定したlockからイメージに入れる（**案**）。
- rootfsは読取り専用のままにする。

## 3 フォント

| 項目 | 内容 | 状態 |
|---|---|---|
| 用途 | PDFへの変換は、デザインの確認に使う。きれいなPDFは利用者が手元で作る | **合意** |
| 入れるもの | Noto Sans CJKとNoto Serif CJKの、RegularとBold（今のイメージと同じ `fonts-noto-cjk`。4ファイルで計93MB） | **合意** |
| 入れないもの | アラビア文字、絵文字 | **合意** |
| タイ文字等のほかの文字 | 入れない | **案** |

- **fontconfig**（**案**）：
  - `sans` はNoto Sans CJK JP、`serif` はNoto Serif CJK JP、`monospace` はNoto Sans Mono CJK JP（Sansのファイルに入っているはずなので、確かめる）。
  - メイリオ、游ゴシック、MSゴシック、Arial、Calibri等はSansへ、MS明朝、Times New Roman等はSerifへ向ける。
  - 文書の言語の指定が中国語や韓国語なら、そちらの字形を優先する。
- **割り切ること**：元のフォントと文字の幅が違うので、改行やレイアウトはずれることがある。

## 4 作業セッションとワークスペース

### 4.1 定義（**合意**）

- 作業セッションは、ワークスペースを引き継ぐ単位。1つの会話、または1つのタスクの実行に対応する。
- 作業セッションとワークスペースは1対1。
- 1つの作業セッションには、直列のRunが複数対応する。Runは時系列に並ぶ。
- 作業セッションの中では、ワークスペースを必ず引き継ぐ。

入れ子とフォークの記録のしかたは**未決**。

### 4.2 ライフサイクル

| | ワークスペース | 履歴（入力の記録、結果、作業の記録） | 状態 |
|---|---|---|---|
| タスクの実行 | Runが終わったら残さない。別の起動へ `work` も `output` も引き継がない | ワークスペースとは別に、DBで管理して残す | **合意** |
| 会話 | 手動でアーカイブするか、古くならない限り保存する | 別に残す | **合意** |

- 保持期間は設定しだいで、設計書の日数は仮の値（**合意**）。
- 自動削除の機能はまだ作らない（**合意**）。
- タスクのデバッグは、特定の実行記録の入力データでセッションを起動し、インタラクティブに動かしながら行う（**合意**）。本番の実行のワークスペースは使わない。
- Skillの修正は、Skillを使って作業している会話の中で、同じワークスペースのまま行う（**合意**）。

**未決**（括弧の中は案）：

- 修正チャットのセッションの切り方（タスクを動かすたびに新しいセッションにし、その後の編集のRunは同じセッションにする）
- 完了したタスクのsnapshot（本番の実行は作らない。修正チャットのタスクのRunは編集のRunが引き継ぐので作る）
- アーカイブの意味（一覧から外してワークスペースを消す。履歴は見られる）
- アーカイブした会話の再開（まずは再開できない形）
- 削除の意味（履歴も利用者から見えなくする）

## 5 サブエージェントとSandbox

親と子でワークスペースを共有する（**合意**）。ほかはすべて**未決**で、機能の議論が先。

- 案：子をRunにせず、親のRunのAttemptの中で動かし、1つのSandboxを親と子で使う。今の「作業セッションと1対1、Runは直列」のまま共有できる。その代わり、子は親のAttemptより長くは生きられない。

## 7 確かめること

試していないので、作る前に確かめる。

- **gVisorでLibreOfficeが動くか**：公開されているスキルの説明には、素の `soffice` がそのサンドボックスでは止まるので専用のスクリプトを使う、とある。Yorikiのrunc・gVisorの両方で試す。
- **LibreOfficeの設定の置き場所**：`HOME` は `/workspace/work/.home` なので、そのままだと設定がsnapshotに入る。別の場所へ向けるかを決める。
- **資源の上限**：LibreOfficeとNode.jsで足りるメモリ・プロセス数。Runtime Profileの初期値を見直す。
- **信頼しない文書を開くこと**：LibreOfficeのマクロを無効にする設定。ネットワークがないことを前提にしてよいかも確かめる。
- **イメージの大きさとビルド**：multi-arch（arm64）のビルドと、Docker Hubへの配布の時間。
- **配布のライセンス**：イメージは公開のDocker Hubに置く前提で、今はMIT・BSD・Apache等を優先している。LibreOffice（MPL）、pandoc（GPL）、poppler-utils（GPL）、Noto（OFL）を入れて配布してよいかを確かめる。
- **外部のSkillのライセンス**：Skillごとに異なる。例えば、確認した時点で `pptx` の `LICENSE.txt` はサービスの外でのコピーの保持や派生物の作成を禁じ、`skill-creator` はApache License 2.0。Yorikiは同梱しないので、取り込むかどうかは導入先が自社の契約で判断する。
