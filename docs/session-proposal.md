# agentセッションの新案

agentセッション、Run、Attempt、ワークスペース、ジョブ、サブエージェント、永続化するものを整理した案。利用者と議論して決めた内容で、設計書へ反映する元にする。今の仕様は、設計書を直すまで design.md・harness.md を正とする。反映したら本書を消す。Sandboxのイメージは [sandbox-proposal.md](sandbox-proposal.md) に書く。

---

## 1 用語

| 用語 | 意味 |
|---|---|
| タスク | 業務の定義（入力、プロンプト、Skill、出口等）。Webhook等で起動される |
| タスクの実行 | タスクを1回動かしたもの |
| 会話 | 利用者が話す画面 |
| agentセッション | 1つの会話画面、または1つのタスクの実行をまとめた概念。履歴と入力を持つ |
| ワークスペース | agentセッションの作業ファイル。agentセッションより寿命が短い |
| Run | Workerを起動する単位。親の動きをひとまとめにした記録と、モデル・版の固定の単位。話の区切りではない。agentセッションの中に直列で、時系列に並ぶ |
| Attempt | 親またはサブエージェントを1つのWorkerで動かす1回分。Workerとコンテナを使うのはAttempt |
| tool call | モデルがToolを呼ぶこと。コマンドもサブエージェントも、これで始まる |
| コマンド | `shell` で動かす1つの実行。親のコンテナの中で、呼出しごとに別の `docker exec` として動く |
| ジョブ | 裏で動いているコマンド。親は待たない |
| サブエージェント | 別のAttemptで、親のワークスペースのコピーの上で動く子 |
| 依頼 | 利用者の1回の発言 |

全部をまとめる総称は置かない。裏で動くものの決まりは「ジョブとサブエージェント」と書く。今のシェルのセッション（design.md §7.5）とログインのセッションと区別するため、「agentセッション」と呼ぶ。

```
agentセッション（履歴、入力）
├─ ワークスペース（0か1つ）
└─ Run（直列）
   ├─ 親のAttempt ─ コンテナ ─ コマンド、ジョブ
   └─ サブエージェントのAttempt ─ 別のコンテナ ─ ワークスペースのコピー
```

## 2 動き

### 2.1 発言と完了の渡し方

- 利用者の発言と、ジョブ・サブエージェントの完了は、親が動いていれば親へ渡し、動いていなければ親を起動する。
- 動いている間は、利用者がいくつでも発言できる。
- 1つのagentセッションの中で、複数の話が混ざってよい。
- Runが終わるかどうかは重要ではない。Workerを使っているかはAttemptで、確定してよいかはagentセッションの状態で判断する。

### 2.2 確定

親が動き終えても、ジョブかサブエージェントが残っていれば、状態は「裏で作業を待っています」になる。親が動き終え、どちらも残っていない時点で確定する。

| | 会話 | タスクの実行 |
|---|---|---|
| 全部止まったとき | 親の応答で一区切り。次の発言を待つ | 業務結果と配信を確定し、終える |

タスクは、終わる時点でジョブとサブエージェントも全部終わっている前提とする。残っていれば止める。

### 2.3 確認待ち

| 確認待ちの間 | Worker・コンテナ | ワークスペース |
|---|---|---|
| ジョブが動いていない | 空ける | 保存して片付ける。回答で展開し直す |
| ジョブが動いている | 動いている間は使う | そのまま。全部止まってWorkerを手放すときに保存する |

- ジョブとサブエージェントは、確認待ちの間も動き続ける。
- 確認待ちの間に終わったら、親は起こさず、回答で動き出すときに結果も渡す。
- タスクの実行の確認待ちも同じ。終わるまでスナップショットは消えない。

### 2.4 ジョブとサブエージェントの共通の決まり

- 親が話し終えた後も動き続け、その間も利用者は会話を続けられる。
- 終わったら親を起こす。
- 時間の上限を置く。値は設定で変えられ、ジョブとサブエージェントで別に設定する。超えたら止めて親に知らせる。
- 止めてよいものは、LLMが積極的に止める判断をする。説明文でそう促す。サーバーのようなコマンドも、この判断で止める。

### 2.5 停止と失敗

- agentセッションの停止で、親もジョブもサブエージェントも全部止まる。1つずつ止める画面は作らない。親は自分の判断で止められる。
- ジョブやサブエージェントの失敗は親へ伝える。LLMが無理と判断したら失敗にし、別のやり方で動かせるなら続ける。

### 2.6 費用

親、ジョブ、サブエージェントの利用量を、agentセッションで合算する。

## 3 ライフサイクル

### 3.1 ワークスペース

消えるのは次のときだけ。

| 対象 | 消えるとき |
|---|---|
| 会話 | 更新されなくなって期限が切れたとき（自動削除はまだ作らない）、アーカイブしたとき、削除したとき |
| タスクの実行 | 完了したとき、異常停止したとき |

- 別のタスクの実行へは、`work` も `output` も引き継がない。
- 期限は設定しだいで、設計書の日数は仮の値。

### 3.2 操作

| 操作 | 履歴・入力 | ワークスペース | 監査ログ |
|---|---|---|---|
| アーカイブ | 残す | 消す | 残す |
| 論理削除（利用者の削除の基本） | 利用者から見えない。実体は残す | 消す | 残す |
| 物理削除 | 消す | 消す | 残す |

監査ログは、これらの操作と独立に残す。アーカイブした会話は、同じ会話のまま、ワークスペースを空で作り直して再開する。LLMには前のファイルがないことを伝える。

### 3.3 履歴と入力

- タスクの起動時に渡された生のデータは、agentセッションに残す。寿命はagentセッションと揃える（個別の保持期限を持たない）。受付で断った要求は残さない。
  - 値の項目
  - ファイル（添付、multipartで受け取ったもの）
  - 入口の本文（Webhookのpayload）
- 結果（業務結果、成果物、配信、作業の記録）も、ワークスペースとは別に履歴として残す。ファイルの中身は保存先に置き、参照と状態はDBが持つ。

## 4 タスクの修正

- 失敗したタスクや出力がおかしかったタスクは、実行記録の入力から一から動かして直す。途中のファイルは使わない。一から動かすとモデルの揺れやデータの変化で再現しないことがある。再現しない程度の問題なら、他の入力でも問題ないようにプロンプトやSkillを直す。
- 実行記録の画面から、その入力で修正チャットを始める。値は入れた状態で開き、ファイルと入口の本文も渡す（同じ保存先のものを参照し、中身を複製しない）。利用者は値を直せる。足りないファイルがあれば、表示して付け直してもらう。
- 動かす定義はタスクの今の版。入力の項目が変わっていたら、合わない値を画面で直す。
- 本番との違い：結果の通知は送らず、入口の受付と重複の判定は通らない。
- 修正チャットは1つのagentセッション。タスクを動かすたびに、ワークスペースを空で作り直す。動き終えたら作業ファイルは残さず、直すときは作業の記録・応答・成果物・入力を見る。動いている最中は、利用者が指示を出してデバッグできる。
- Skillの修正は、Skillを使って作業している会話の中で、同じワークスペースのまま行う。

画面はagentセッションを単位とし、タスクの実行1回を1行で見せる。中のRun等はagentセッションの詳細で見せる。

## 5 ワークスペースとコンテナ

- ワークスペースはコンテナの外からマウントする。コンテナに永続的に残すものはなく、いつでも捨てて作り直せる。
- Attemptの始めに最新のスナップショットを展開してマウントし、Workerを手放すときに保存する。残すのは最新の1つだけ。
- マウント先はWorkerのディスク。今のtmpfsをやめる。
- 親もジョブも動いていなければ、コンテナを片付ける。
- 保存に失敗したら再試行し、それでも駄目なら失敗にする。黙って進めない。
- タスクの実行は、完了の時点でスナップショットを作らない（確認待ちでは作る）。
- Workerが落ちたら、そのAttemptの作業ファイルが失われたことをLLMに伝える。LLMが確かめて作り直す。発言、返答、Toolの結果等の文脈はDBに残る。別のWorkerでは、スナップショットから展開する。

**作る前に確かめること**：容量の上限（tmpfsの `size` の代わり）、ディスクの速さ、Workerのディスクへ書かせることとSandbox脱出への対策の関係。

## 6 永続化するもの

| 対象 | 持ち主 | いつまで |
|---|---|---|
| 会話の履歴（メッセージ、作業の記録） | agentセッション | agentセッションが残る間 |
| タスクの入力と結果 | agentセッション | 同上 |
| 文脈（Runの記録） | Run | 同上 |
| 添付・成果物 | agentセッション | 同上 |
| サブエージェントの記録と報告 | 親の履歴 | 同上 |
| ワークスペース（最新のスナップショット） | agentセッション | §3.1 |
| 監査ログ | 独立 | §3.2 |

永続化しないもの：動いているプロセスとジョブ、シェルの状態、コンテナ。

## 7 サブエージェント

- 別のAttemptで動く。どのWorkerでもよい。
- ワークスペースは、動かす時点の親のワークスペースのコピー。親のコマンドが書き込み中でもその時点のファイルを写し、書き込み中のファイルの中身は保証しない。親の変更は子から見えない。
- 親に返すのは、報告と差分。差分はシステムが始めと終わりを比較して作る。バイナリは変わったファイルの一覧とファイル自体を渡す。
- 取り込みは親が判断する。競合したら親が直す。
- 報告は、指示の権限を持たないものとして親へ渡す。
- 成果物は作らない。子の `/workspace/output` は親へ渡さない。成果物を作る作業は親が行う。
- 親が待つだけなら、親はAttemptを終えてWorkerを空ける。
- 子の作業の記録は、親の履歴の中に入れ子で見せる。子の文脈は親のものと混ぜない。
- 差分を返したら、子のワークスペースは消す。

| 機能 | 決定 |
|---|---|
| 同時に動かす | 動かす |
| 終わった子に続きを頼む | まずは作らない |
| モデルとeffort | 親のLLMが選べる（既定は親と同じ）。利用者向けの画面は作らない。選べるのはagentセッションで使えるものだけ（機密ならローカルLLM） |
| 利用者への質問 | 子は聞かない。困ったら報告で親へ返す |
| 種類の定義 | まず組込みだけ |
| Skill | 読み込んで使える。Skillの変更はできない |
| タスクの実行で使う | 使える |
| 孫 | 作らない |
| フォーク（親の文脈を引き継ぐ子） | 入れない |

## 8 他のハーネスとの関係

確認した範囲（2026-11-05 時点。手元のコードは2026年10月17〜20日の版）では、Claude Code・OpenCode・Codex CLIは、裏のものをターンではなくセッションやスレッドの下に置き、ターンが終わっても動かし、終わると親を起こす。Gemini CLIのサブエージェントはToolの呼出しの中で動くようである。DeepSeek HarnessとOpenHandsは未確認。Yorikiのサブエージェントがワークスペースのコピーの上で動く点は、Claude Codeの既定（同じファイルを見る）とは異なる。
